## Objective

Close the open housekeeping and upgrade issues as nine PRs, one branch each, cut sequentially from merged `main` in the main checkout, each with at least two Codex review rounds and green CI before merge. Priority is tech-debt reduction: this machine (and margo) are the only users, so no shims, no compatibility layers, no migrations beyond what a deletion needs.

### User
Mark, the single operator. He runs Bakin on this box (dev loop on 3737) and on margo (compiled release, rc.41). He wants the batch merged without live-testing each PR, then one manual sweep on 3737 before the next release (interview Q10, option C).

### Success looks like
- `main` has none of the one-shot approvals upgrade code, and `doctor.escalation` is a boolean with no string coercion.

- `bun run lint` is a binary gate (`--max-warnings 0`) with React rules on, and every `set-state-in-effect` instance is gone.
- The browser loads exactly one zod (`/vendor/zod.js`), the SDK declares zod as a peer, every bundle that carried a private copy shrinks, and Bits builds against the same contract.
- Health has an Updates tab fed by one engine, the four old "update available" probes are deleted, background checks run on a schedule, and `bakin updates` reports the same records.

## PR 3 — #896 delegation awareness + lock hardening

Facts: part 1 (cross-process single-flight) is delivered by #895 — O_EXCL lock files (`packages/core/src/operations/resources.ts:188-209`), every installer asserts its lock (`media/installer.ts:91`, `adapter-antfly/src/models.ts:384`, `bin-installer.ts:184,254`), the CLI routes to a running server (`src/cli/operation-mode.ts:24-38`), and a second attempt waits visibly then returns `noop`. Part 2 is open: only approval-backed applies write `applying` (`doctor-approvals.ts:430`); a Health-UI apply (`plugins/health/index.ts:665-703`) and escalation's own safe auto-apply (`doctor-escalation.ts:257-280`) leave nothing that `assessRepairCoverage` or `delegateDoctorRepair` read. An operation is invisible to `registry.list()` until its `validate` resolves (`registry.ts:535-545`), so a map populated inside validate is not an exclusion mechanism **(C2)**.

| # | Decision |
|---|----------|
| D3.1 | **Atomic incident reservation (C2, R2).** `src/core/doctor-repair.ts` owns a synchronous in-process admission map `incidentId → ownerToken` (one server process; durable ownership stays the operation registry's job). `reserveIncidents(ids, owner) → Reservation \| { refused: { overlapping: string[], heldBy } }`: granted when every id is free; **attached** (granted, shared) when every overlapping id is held by the SAME owner token; refused when any id is held by a different token. A repair's owner token IS its operation fingerprint (`repair:<planId>:<sortedItemIds>`), so two identical `startDoctorRepair` requests reserve-attach exactly as the registry attaches them (`tests/core/doctor-repair.test.ts:205` keeps passing). Taken BEFORE `startOperation` by every apply path (UI, approval, escalation, Discord — all enter `startDoctorRepair`), by `delegateOnce` before creating a task, and by escalation for its planning span. Released by the holder on operation settle (success, failure, cancel, validate rejection) or when the holder's own span ends; never durable — a restart drops them and startup recovery re-judges from fresh state. |
| D3.2 | **Escalation owns what it is judging (R2).** `doctor-escalation.ts:240`: `remaining = fresh.filter(i => !covered.has(i.id) && !held.has(i.id))` (logged with `{ held }`), then `reserveIncidents(remaining, 'escalation:<cycleId>')` for the planning await. After planning, `transfer(subset, newOwner)` moves the safe-item incidents ATOMICALLY to the auto-apply operation's fingerprint token (released by that operation on settle); escalation KEEPS every untransferred incident until its disposition is recorded — repair approval request written, navigate approval written, delegation request written, operator-review request written (D3.4) — releasing each subset at that point, and releases everything on any throw. **Delegation is a handoff, not a fresh reservation (R2′):** `delegateDoctorRepair`/`delegateOnce` take an optional `reservation` (the caller's owner token); escalation passes its own, so the delegate path `transfer`s those incidents to the delegation token instead of reserving, keeps them through request + task persistence, and releases them once the request file is written; an external `POST /doctor/delegate` with no reservation reserves fresh under its own token (and is refused while escalation holds the incidents). Test: the mixed safe/manual/delegated cycle actually creates its delegated task. A UI repair that starts mid-await is therefore refused (D3.3's `repair_in_flight`) instead of racing. The next cycle re-judges once the repair verified or failed. |
| D3.3 | **Refusal is a first-class result (R10).** `delegateOnce` returns `{ status: 'repair_in_flight', overlapping, heldBy }` when reservation is refused — never a task. Consumers move in the same PR: `POST /api/plugins/health/doctor/delegate` answers `409 repair_in_flight` (body carries the union); **the CLI transport decodes it (R10′):** `src/cli/http.ts`'s `apiPost` turns every non-2xx into an unstructured exception (`http.ts:122`), so the delegate command uses a variant that accepts an `expect: { 409: repairInFlightSchema }` map and returns the decoded union for recognized statuses while every other error keeps today's path; the plain, TTY and JSON renderers handle a result with no `request`/task (plain: one line naming the holder; TTY: no "board task created"; JSON: the union verbatim) and exit 1; the Health UI's delegate dialog shows the refusal inside the dialog. Tests: command-level with a mocked 409 response for all three renderers incl. exit code, plus the route. |
| D3.4 | **Failed or unplannable safe repair → operator, never an agent (Q3 = A; C14, R4).** (a) A repair-type incident that remains after its safe auto-repair failed opens ONE review task with a `health-repair` approval; `RepairProposal` gains `failure?: { operationId, stage, error, at }` (type + stripping schema + card rendering) so the frozen proposal carries the receipt. (b) When planning throws, returns no executable item, or the auto-apply operation settles without an apply report (today `doctor-escalation.ts:269` THROWS and exits the cycle — it now records the receipt and falls through to the partition), the repair-type incident opens a review task WITHOUT an approval (nothing to apply). **That fallback has a durable lifecycle:** a new request kind `operator-review` in `doctorRepairRequestSchema` (`kind` enum + `failure` receipt on the request), written like `delegate` requests with `taskId`, `incidentIds`, `checkIds`; `judgeCoverage` treats an open `operator-review` request as covering its incidents under the same cooldown/stale window; resurfacing (`doctor-escalation.ts:170-185`) never attaches a `health-navigate` approval to it — it escalates the SAME task to Review with operator-review copy ("Health: the repair failed again / could not be planned — needs you") and records the event; auto-close (`doctor-autoclose.ts`) completes it when the originating checks verify healthy on a fresh targeted run, as for every other kind. Agent delegation is reserved for incidents with no repair action. |
| D3.5 | **Stale-lock reclaim race.** ~~reclaim takes an O_EXCL `<lock>.reclaim` marker, re-reads under it, unlinks only the judged holder~~ — **superseded during PR 3 review (Codex rounds 1–2 showed every unlink-based reclaim keeps a two-contender window):** resource locks are now held by **flock(2)** on an open descriptor (`bun:ffi` → libc); the kernel releases a dead holder's lock, no process ever unlinks another's file, acquisition pins the inode and release unlinks-then-closes. Cross-process tests in `tests/core/operations/resources.test.ts` (live foreign holder with empty metadata, dead-holder takeover, barriered two-process race with disjoint intervals). `bootId` stays recorded-only (pid reuse is moot under flock). |

## Code Style
Existing conventions apply (CLAUDE.md). The one shape this batch adds, an update source (shown against the D7.9 contract):

```ts
// src/core/updates/sources/search-engine.ts
import { createLogger } from '@/core/logger'
import type { UpdateSource, UpdateObservation } from '../types'

const log = createLogger('updates:search-engine')

export const searchEngineSource: UpdateSource = {
  kind: 'search-engine',
  group: 'required',
  network: false,
  async observe(ctx): Promise<UpdateObservation[]> {
    const check = await ctx.search.setup.dependency.check()          // adapter-neutral; antfly stays behind the factory
    if (!check.applicable) return []                                    // guest / disabled / refused: no row at all
    if (check.installed && check.required && check.installed.version !== check.required.version) {
      return [pinMismatch(check.installed, check.required, ctx.fingerprint('search-engine'))]
    }
    if (check.status === 'ok') return [current(check.installed, ctx.fingerprint('search-engine'))]
    log.warn('search engine check inconclusive', { status: check.status })
    return [unknown(check.message, ctx.fingerprint('search-engine'))]
  },
}
```
Sources are pure observers: they never write, never start operations, never broadcast. The engine owns persistence and events; actions are started by the apply service.
