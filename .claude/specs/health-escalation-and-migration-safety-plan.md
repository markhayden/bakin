# Implementation Plan: Health Escalation, Task Liveness & Runtime-Migration Safety

Spec: `health-escalation-and-migration-safety.md` (same directory). Revision 2 (after Mark's source-based plan review, 2026-10-01). Approved 2026-10-01.

## Context

Margo's blocked column fills with system-created tasks because five Bakin bugs reinforce each other: escalation delegates operator-only incidents to an agent every 12 h; task order collides by construction; the stale-task check reads agent heartbeat files instead of the ledger and flags the repair task itself; triage hand-offs and dependency continuations leave tasks in progress with no run for 35 min; and runtime-switch adoption copied an OpenClaw internal cron marker into the schedule. The fix is three stacked PRs: (1) liveness and flow, (2) approvals in core with a new escalation policy and the board as the inbox, (3) schedule migration safety. Everything ships via PRs; margo is never edited by hand.

## Plan-review revisions (what changed from rev 1)

| # | Review point | Resolution in this plan |
|---|-------------|-------------------------|
| R1 | Approvals cannot depend on ephemeral repair plans (`doctor-repair-plans.ts`: in-memory, 10-min TTL, preconditions invalidated by re-runs). | The `health-repair` owner persists the **frozen proposal**: `actionId`, `safety`, and the full `changes[]` (kind/target/action/description) per item, plus the originating `observationIds` and report id. At resolve: re-plan against fresh evidence, canonicalize both change sets (sorted `actionId|kind|target|action`), and apply only when equal; a differing set cancels the approval with reason `plan-changed`, logs it on the task, and re-escalates a fresh approval. The repair request gets an `applying` state written **before** the apply call and an `applied` event after; boot rehydration treats a request stuck in `applying` as interrupted → runs targeted verification → completes or re-opens a new approval. Tests: delayed approval (TTL expired), restart between request and resolve, simultaneous Health + Discord clicks (store resolve is compare-and-set on `status: pending`; second caller gets 409), interruption after mutation before `applied` (PR 2 T7). |
| R2 | "Remove every unrunnable job" is too broad for an incident-scoped approval. | The plan item's `changes[]` freezes the exact job ids (one `{kind:'file', target: jobId}` change per job); `apply(items)` deletes only ids present in the items it receives, re-checks each is still a Bakin job failing the predicate (else `skipped`), and never touches ids outside the frozen set. The confirmation body names every job. R1's change-set comparison means a job appearing after the approval invalidates it (fresh proposal differs). Tests: approve with A+B frozen while C appears afterwards → A+B removed, C untouched, next cycle proposes C (PR 3 T9). |
| R3 | Settle-time hand-off could park a healthy workflow parent whose card owner differs from the step agent. | The rule applies only to `opts.dispatchKind === 'regular'` turns (`dispatch-turns.ts:735`; workflow step turns fire with `'workflow'` from `dispatch-workflow.ts:203`). Explicit tests: parallel steps, a nested workflow parent, and a card owner ≠ step agent all settle without a park (PR 1 T6). |
| R4 | Auto-close must require fresh successful verification, not an absent incident id. | `reconcileRepairRequests` runs `runTargetedDiagnostics(originatingCheckIds)` (the check ids behind `request.observationIds`) and closes only when every originating check evaluated **ok/healthy** (not unknown, error, stale, timed out, or unregistered) AND none of `request.incidentIds` is present. A request in `applying` is skipped. Closing cancels the pending approval (`cancelApproval(id, 'resolved')`) and the cancel is broadcast. Tests cover each negative evidence state (PR 2 T9). |
| R5a | Existing workflow gates: old records must be preserved and gates pending without records reconciled before the board signal switches to core records. | One-shot `src/core/approvals/records-upgrade.ts` (same deletable class as the settings upgrade): on boot, before plugin init, every `~/.bakin/workflows/approvals/*.json` record is re-written into `~/.bakin/approvals/` with owner `{kind:'workflow-gate', …}` and its deliveries intact (so live Discord cards keep resolving), then the old directory is removed. Workflows' `onReady` then runs `ensurePendingGateApprovals()` which creates a record for every `pending_approval` instance lacking one (idempotent by approvalId). The board signal switch (T10) is ordered after both. Spec derived decision "pending records are not migrated" is reversed. |
| R5b | `doctor.escalation` persisted strings must be converted, not just retyped. | The settings upgrade maps `'off' → false`, `'notify' → true`, `'task' → true`, missing → default `true`; `normalizeDoctorSettings` applies the same coercion on every load until the upgrade file is deleted. Tests: repeated run is `noop`, interrupted run (settings written, workflows.json not yet stripped) resumes to the same end state (PR 2 T2). |
| R6 | Heartbeat bumps need execution identity; a by-task bump can keep a dead sibling step alive. | Stream-chunk bumps use the exact run id (`opts.threadId`). Exec-tool calls carry only agent + task id on both transports (`provider.ts:58`, `mcp-server.ts:142`), so the new `bumpHeartbeatByTaskAgent(taskId, agent)` updates `runs WHERE task_id=? AND agent=? AND status='running'` **only when exactly one row matches**; zero or several matches bump nothing and log at debug. `logProgress` uses the same rule (its `bumpHeartbeatByTask` is deleted). Tests: two concurrent steps on one task, only one producing activity → only its row advances; same-agent parallel steps → no bump (PR 1 T1/T2). |

## Architecture (what each PR adds)

**PR 1 — liveness & flow**
- `src/core/task-liveness.ts`: `isStrandedInProgress`, `stepExecKey`, `assessWorkflowRuns`, `bumpRunHeartbeat(runId)`, `bumpTaskRunHeartbeat(taskId, agent)` (R6 rule). The ledger is the only liveness signal; both private `isAgentHeartbeatStale` copies are deleted. Workflow steps are keyed `${effectiveTaskId ?? taskId}:${stepId}` (nested workflows claim runs on the child id, `dispatch-workflow.ts:174`).
- Settle-time hand-off (regular turns only) generalizes the decomposition park; continuation re-queues an in-progress parent with no live run.
- Task order: index entry gains `order`; `nextOrderSync(column)` = max+1; `countByColumnSync` deleted.
- CONTACTS.md line deleted; `ensureBinDirsOnPath` adds `dirname(process.execPath)`.

**PR 2 — approvals in core & escalation policy**
- `packages/core/src/approvals/` (record store, zod, owner union `workflow-gate | health-repair | health-navigate`, records at `~/.bakin/approvals/`, compare-and-set resolve) + `src/core/approvals/` (kind registry, `requestApproval`/`resolveApproval`/`cancelApproval`, rehydration, ONE channel subscription, one-shot settings + records upgrades). SSE events `approval.pending` / `approval.resolved`.
- Host: `GET /api/approvals?status=pending&taskIds=`, `POST /api/approvals/:id/resolve`; host-owned attention provider (toast + OS); duplicate OS notification in `use-sse.ts` deleted.
- Workflows registers the `workflow-gate` kind; the engine always creates a record; plugin-owned store/rehydration/wiring/badge provider deleted; gate routes become thin wrappers.
- Doctor: `health-repair` (frozen proposal, R1) + `health-navigate` kinds; policy = auto-apply safe → approval tasks in `review` → delegate the rest; evidence-gated auto-close (R4); `notify` mode deleted; `doctor.escalation` boolean + System & Alerts field.
- Tasks: `useTaskApprovals` drives the "Needs approval" signal from pending records; `ApprovalPanel` per kind in task detail.

**PR 3 — schedule migration safety**
- `isTaskPrompt(command)`: trimmed non-empty AND contains whitespace. Enforced on create/update/adopt/ensureBakinJob (400) and in the job form.
- Adoption returns `{adopted, skipped, refused, failed, listing}`; CLI and Runtime hub print one line per source job.
- Schedule health: sidecar helpers; `schedule-sync` reports non-prompt orphans as runtime-internal; new `schedule-prompts` check with a destructive `remove-unrunnable-jobs` repair whose items freeze job ids (R2) → surfaces as an approval task via PR 2.
- Survival test pins the openclaw→pi→openclaw round trip.

## Decisions made during planning (flagged, none blocking)
1. `requireRejectReason` moves to `settings.approvals` with `channel`/`channelAlerts` so workflows keeps zero approval settings.
2. Dismiss on an action-required incident = snooze 7 d (`health-acks.ts:126` refuses permanent ack on that tier); lower tiers = ack.
3. Health approvals use option ids `apply`/`dismiss`; OpenClaw native buttons accept only `approve`+`reject` (`approval-helpers.ts:37`), so on OpenClaw they render as message + link. `apply` is `primary` (no reason modal); the click is the confirmation.
4. A triage turn that neither assigns nor completes is not parked; the watchdog remains the backstop.
5. "Remove job" is one batch item naming every frozen job id (R2).

## Branch & commit strategy

- Branches in the main checkout (3737 serves the tip): `feat/task-liveness-and-flow` → `feat/approvals-in-core` → `feat/schedule-migration-safety`, opened as a native `gh` stack (`gh pr create --base <previous-branch>`). Each PR merges only after Mark's live test of its tip; the next branch rebases on main after merge.
- One conventional commit per task; each commit leaves typecheck + lint + the touched test files green so any commit is a rollback point (`git revert <sha>` is clean; task commits do not share files with neighbours except where noted).
- Every push is preceded by `bun run typecheck && bun run lint && bun run check:cycles && bun run test` (UI commits add `bun run ui:conformance --quick`; CP-D and the PR 3 tip run `--full` + `ui:test:conformance`).
- Plugin manifest bumps ride the last task of each PR. `generated-version.ts` is never committed.
