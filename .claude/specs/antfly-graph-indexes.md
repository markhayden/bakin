## Context

Bakin's search system after `feat/multimodal-search` uses:

- Hybrid BM25 + semantic search via Antfly RRF fusion
- Per-content-type embedding templates via `embedderRef` (BGE for text, CLIP for images)
- Server-side PDF and text content extraction fed into a `content` field
- Cross-encoder reranking on single-modality tables
- Schema migration state file to force drop+recreate on embedder/schema changes

That covers retrieval. What it doesn't cover is **relationships** between documents. The things search can't answer well today:

- "Show me every task that references project X, every asset attached to those tasks, and every audit entry for those tasks in the last week."
- "Given this message from the main agent, what's the graph of tasks, assets, and prior messages that relate to the topic?"
- "Which projects have the most interconnected task graphs versus which have flat to-do lists?"
- "Show me the lineage of a piece of content: the original brainstorm → the planning task → the work task → the review task → the published asset."

Those are **graph queries**, not search queries. RAG retrieval can fake them with follow-up calls (search for X, then for each result search for Y), but the latency and hallucination surface make it a poor fit. A proper graph query engine runs them as one primitive.

## What Antfly provides

Antfly supports graph queries natively via `GraphQuery` in the query API. Relationships are modeled as edges between document rows, stored in a dedicated graph index per table, and traversable inside a query:

### Key capabilities from the survey

(All references are to `/Users/markhayden/go/src/github.com/antfly/antfly/`)

- **Graph index type** — `src/store/db/indexes/graph_index.go` — a dedicated index that stores edges alongside the normal full-text and embedding indexes. Edges live in Pebble under the shard's storage root.
- **Automatic relationship extraction** — Antfly can extract entities and relationships from document text during enrichment and auto-populate the graph index. This happens server-side via Termite/NER. Requires an NER model pulled via `antfly termite pull`.
- **Topology constraints** — one-to-one, one-to-many, many-to-many. Enforced at write time.
- **TTL on edges** — edges can expire independently of their documents. Useful for temporary associations (e.g. "this task is currently watched by the main agent").
- **Query composition** — `GraphQuery` inside a `QueryRequest` runs a graph traversal over search results. The `expand_strategy` field (`union` | `intersection`) controls how graph results merge with the hybrid search results. The result is a single response with search-ranked documents plus a traversal subgraph.
- **Declarative query DSL** — graph queries are JSON objects describing node and edge filters, not custom Cypher-like strings.

### Documented examples from Antfly

See `/Users/markhayden/go/src/github.com/antfly/antfly/docs/guides/` (grep for `graph_search` or `GraphQuery`). The quickstart guide has a mid-length worked example; the hybrid-search guide has a short mention. Bakin's own survey found these three files particularly useful:

- `src/store/db/indexes/graph_index.go` — the index implementation, the schema of an edge
- `src/metadata/api.go` — where `GraphQuery` is accepted at the REST layer
- `src/metadata/retrieval_agent.go` — how the built-in retrieval agent composes graph traversal with hybrid search

## What the Bakin integration could look like

### Schema sketch

Bakin content already has natural relationships:

| From | To | Edge type |
|---|---|---|
| `bakin_tasks.task` | `bakin_projects.project` | `belongs_to` |
| `bakin_tasks.task` | `bakin_assets.asset` | `produces` (asset generated by task) |
| `bakin_tasks.task` | `bakin_tasks.task` | `blocks`, `duplicates`, `related_to` |
| `bakin_assets.asset` | `bakin_tasks.task` | `attached_to` (inverse of `produces`) |
| `bakin_audit.event` | `bakin_tasks.task` | `audit_for` |
| `bakin_workflows.workflow` | `bakin_tasks.task` | `spawned_by` |
| `bakin_messaging.message` | any | `references` (resolved by NER during enrichment) |

All of these are already implicitly present in the data — `task.projectId`, `asset.taskId`, audit entries with `taskId` in their payload. The graph index would explicitly materialize these relationships and make them queryable.

### Integration points

1. **Edge declaration** — new optional field on `SearchContentTypeDefinition`:
   ```typescript
   edges?: Array<{
     name: string           // 'belongs_to', 'produces', ...
     sourceField: string    // field on this document holding the target key
     targetTable: string    // which table the target lives in
     topology: 'one-to-one' | 'one-to-many' | 'many-to-many'
   }>
   ```
   The registry would translate these into Antfly graph-index config at table creation time, same pattern as `indexes[]` in T3.

2. **Cross-document traversal in queries** — new optional field on `SearchQueryParams`:
   ```typescript
   graph?: {
     traverse: Array<{ edge: string; direction: 'out' | 'in'; depth?: number }>
     expandStrategy?: 'union' | 'intersection'
   }
   ```
   Passed through to Antfly's `GraphQuery`. Responses include the traversed subgraph alongside the ranked documents.

3. **Automatic relationship extraction (optional)** — configure the NER model per content type so Antfly can extract entity references from long-form text like task descriptions or audit entries. Requires pulling an NER model via `antfly termite pull` and wiring the name through `embedders`-like config.

4. **UI surfaces** — new "Related" sidebar on task detail pages showing the local subgraph. New graph visualization on the Ask page (once #70 ships) so the retrieval agent can show "here's what else I found along the way."

### What changes in the user-facing product

- **Task detail pages** get a "Related" panel with one-hop neighbors across tasks, assets, audit entries, and messages. Today the closest thing is the "linked assets" list, which is manually maintained.
- **The Ask feature (#70)** gets meaningfully smarter. A question like "what went wrong with the deploy last week" can expand from the initial audit-entry hit to the related tasks, linked assets, and referenced messages in one query instead of N round trips.
- **Cross-project analytics** become possible — "which projects have the most interconnected task graphs?" is a single aggregation query over edge density instead of a batch script.

### What stays the same

- The registry, embedder-resolver, rerankField semantics, and multimodal indexing from T1–T7. Graph indexes are additive — they ride on top of the existing per-table infrastructure.
- Bleve full-text and semantic search still run for every query. Graph traversal happens *after* initial retrieval and *merges* with the ranked set.
- The migration mechanism. Adding graph indexes to a content type is a schema change and would bump `SCHEMA_VERSION` to force a drop+recreate. Existing content types without edges keep working unchanged.

## Dependencies and blockers

### Hard blockers — must be resolved upstream before Bakin ships

- **Relationship extraction model** — if we want automatic edge population from free text, we need an NER model pulled via Termite. Pre-trained models exist (spaCy's `en_core_web_trf`, Hugging Face `flair/ner-english-ontonotes-fast`). Would need to verify which Termite supports and pull it via `antfly termite pull`.
- **Graph query result shape stability** — Antfly's `GraphQuery` response shape in `/api/v1/query` needs to be stable enough for Bakin to parse and render. Verify by writing a small probe against the dev Antfly and checking the schema matches `src/metadata/api.yaml`.

### Soft blockers — nice-to-have before starting

- **Bakin #72 settled.** The multimodal branch discovered multiple upstream Antfly bugs (dead `content_security` config, broken PDF library, ONNX reshape in CLIP batching, viper defaults disrupted by `--config`). Graph indexes would probably find more. A future spec session should wait until #72 is at least acknowledged upstream to know whether these get fixed in a reasonable timeframe or we build permanent workarounds.
- **The Ask feature (#70) in flight.** Graph traversal is most valuable paired with a natural-language query surface that can explain what it found. Shipping graph indexes alone without Ask is a half-feature — you get the data but no UX to consume it. Either ship Ask first (current plan) or ship graph + Ask together.

## Why not do this now

Four reasons:

1. **Multimodal search isn't battle-tested yet.** T1–T7 just shipped. Let it bake for a few weeks of real usage before piling more on top.
2. **#70 (Ask Bakin) is the next feature with real user value.** A natural-language query UI for the existing hybrid search is a bigger immediate win than graph traversal.
3. **Relationship extraction is a research problem.** NER quality varies wildly by domain. Before committing, we'd want to validate that the extracted relationships are actually useful on Bakin's real content, not just theoretically interesting.
4. **Antfly's graph query API may still be evolving.** It's in the docs but we haven't probed how stable the JSON shapes are. A spec session starts with a day of playing with the actual API against a test table before designing the schema.
