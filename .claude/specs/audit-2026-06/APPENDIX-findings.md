## [arch-layering] images plugin imports assets plugin internals directly, bypassing the HookRegistry

**Severity:** P1 (verifier: P1)

**Files:** `plugins/images/lib/tools.ts`, `plugins/assets/index.ts`

**Evidence:** plugins/images/lib/tools.ts:6-8 — `import { getAsset, listAssets, upsertFromSource, resolveStoreFile } from '../../assets/lib/asset-service'`, `import { isValidAssetId } from '../../assets/lib/asset-id'`, plus `AssetManifest`/`AssetVersion` types from '../../assets/lib/manifest'. CLAUDE.md (Plugin Communication) states cross-plugin calls go exclusively through the HookRegistry with 'No direct imports between plugins', and the assets plugin actually registers the equivalent hooks (plugins/assets/index.ts:407-448: assets.listByTask, assets.resolveServe, assets.saveFromSource, assets.purgeClipboardForTask) — images sidesteps them with relative imports into the sibling plugin's lib/. This also bypasses the plugin-permission layer (src/lib/plugin-permissions.ts gates ctx.* surfaces, not raw module imports) even though images declares assets.read/assets.write in its manifest. This is the only plugin-to-plugin import in the repo (verified by sweep across all 10 plugins).

**Recommendation:** Route images' asset writes/reads through the existing assets.* hooks (extend assets.saveFromSource / add an assets.upsertFromSource hook for the manifest-returning path), or promote asset-service into packages/core if it is genuinely shared infrastructure. Then add a guard (see guard-gap finding) so the pattern cannot recur.

**Verifier reasoning:** Every cited fact verified by reading the files. plugins/images/lib/tools.ts:6-8 directly imports getAsset/listAssets/upsertFromSource/resolveStoreFile from ../../assets/lib/asset-service, isValidAssetId from ../../assets/lib/asset-id, and manifest types — used as real value imports at lines 229, 235, 244, 379-399, 442, 452. The rule it violates is explicit: CLAUDE.md Plugin Communication and .claude/knowledge/plugin-system.md:1118 ("No direct imports between plugins or from core → plugins"). The assets plugin does register the sanctioned hooks at plugins/assets/index.ts:407-448 (assets.listByTask, assets.getAssetTypes, assets.resolveServe, assets.saveFromSource, assets.purgeClipboardForTask). My independent sweep confirms images→assets is the only sibling-plugin import in plugins/** (all other ../../ imports target src/core or packages/core). The permission-bypass claim also holds: src/lib/plugin-permissions.ts:64-68,233 gates only ctx.assets method calls via wrapObject, and upsertFromSource/listAssets/resolveStoreFile are not even on the gated AssetsAPI (packages/core/src/plugin-types.ts:631-639), so the raw imports sidestep the declared assets.read/assets.write grants. Mitigations keep this at P1 rather than P0: images declares dependencies:["assets","models"] in its manifest; the assets watcher self-heals indexing and emits asset.changed on any manifest write (plugins/assets/index.ts:329-346), so direct upsertFromSource causes no data loss; and core plugins are statically bundled so nothing breaks at runtime today. One nuance for the fix: neither ctx.assets nor the existing hooks cover everything images needs (filtered listAssets, manifest-returning upsert, resolveStoreFile), and core itself dynamic-imports plugins/assets/lib/asset-service to implement ctx.assets (src/lib/plugin-context-services.ts:133-146) — evidence that promoting asset-service into packages/core is the structurally honest remedy, exactly as the finding's second recommendation suggests.

**Evidence:** scripts/lib/registry.ts is the runtime exec-tool registry (globalThis-backed Map, builds full PluginToolContext with storage/search/runtime facades) imported by production server code: src/core/mcp-server.ts:34 and :44-48 (which also imports scripts/lib/{log-progress,post-channel,get-paths,heartbeat,search-tools} for self-registration), src/lib/plugin-registry.ts:46, src/core/plugin-host/reload-pipeline.ts:39, and packages/host/src/api/exec-tools/[toolName].ts:9. So a directory the repo treats as build tooling (and that this audit's lint/test scopes treat as scripts) ships in the compiled binary's module graph. Separately, scripts/bin/post-channel.ts:1 has shebang `#!/usr/bin/env npx tsx` in a Bun-only repo (tsx is not how anything else runs here) and prints its own warning that it 'bypasses Bakin tracking (no MCP call, no Health metrics, no audit log)'.

**Recommendation:** Move scripts/lib/* into src/core/exec-tools/ (or packages/core) so the production module graph contains no scripts/ paths, leaving scripts/ purely build/dev tooling. Fix or delete scripts/bin/post-channel.ts (bun shebang, or remove — the MCP tool is the supported path).

## [tooling] Imitation Crab usage-seeding module is bundled into the production binary and activates via a single env var

**Files:** `server.ts`, `dev/imitation-crab/usage-seed.ts`

**Evidence:** server.ts:815-819: `if (process.env.BAKIN_SEED_USAGE === '1') { import('./dev/imitation-crab/usage-seed').then(m => m.seedMockUsage())... }`. The specifier is a static string, so `bun build --compile` bundles the mock module into release binaries — verified: `strings dist/bakin-darwin-arm64 | grep imitation` shows the embedded source comment `// dev/imitation-crab/usage-seed.ts`. usage-seed.ts imports src/core/usage's recordUsage and fabricates MCP/REST/agent usage entries (fake tool names like bakin_exec_post_discord), so setting BAKIN_SEED_USAGE=1 on a production install pollutes the health dashboard's usage feed with synthetic data. Damage is bounded (the recorder is in-memory), hence P2 rather than P1.

**Recommendation:** Gate the import on BAKIN_DEV as well (like the hot-reload coordinator at server.ts:827), or move seedMockUsage behind the imitation-crab gateway/dev.ts side so dev/ code is never in the compiled module graph; alternatively have build-binary.ts fail if the bundle contains dev/imitation-crab paths (extend assert-production-assets).

## [tooling] Embedded-assets codegen interpolates paths into string literals without escaping

**Files:** `scripts/generate-embedded-assets.ts`

**Evidence:** emitManifest builds the generated module with raw template interpolation: generate-embedded-assets.ts:204 `import ${a.varName} from '${spec}' with { type: 'file' }` and :209 `['${a.urlPath}', ${a.varName}],` — neither spec nor urlPath is escaped. A file under packages/host/public/, plugins/*/dist/, or packages/host/src/data/ whose name contains a single quote, backslash, or newline produces a syntactically broken _embedded-assets-static.ts. The failure is loud (the next compile fails), so this is fragility rather than a silent-pass risk; today all walked filenames are build outputs with safe names.

**Recommendation:** Use JSON.stringify() for both the import specifier and the map key when emitting the module (one-line change each), making the codegen safe for any filename.

## [tooling] Five ad-hoc recursive directory walkers across scripts with inconsistent ignore rules

**Files:** `scripts/generate-embedded-assets.ts`, `scripts/assert-production-assets.ts`, `scripts/docs/source-scan.ts`, `scripts/docs/check.ts`, `scripts/docs/generate.ts`

**Evidence:** Each script reimplements recursive walking with different skip lists: generate-embedded-assets.ts:73-90 (walk; skips only .map files), assert-production-assets.ts:13-26 (walkFiles; no skips at all — it walks every plugins/<id> subtree including any node_modules/ that appears, then filters by suffix), source-scan.ts:66-74 (walkFiles; skips node_modules/dist/.astro), check.ts:45-52 (walkMarkdown; no skips), generate.ts:215-225 (inline walk inside updateGeneratedContentBlocks; no skips). None share code, so ignore-rule fixes (e.g. excluding a future plugins/<id>/node_modules) must be discovered and applied five times.

**Recommendation:** Add a single scripts/lib-build/walk.ts (or use Bun.Glob, already available in the runtime) with explicit ignore options, and migrate the five walkers during the docs-generator split.
