## A. #855 — non-raster images never reach a vision model

### Objective

Asset enrichment sends raw SVG bytes to the vision API, which rejects them
(`supported: image/jpeg, image/png, image/gif, image/webp`). Every attempt is a
billed runtime turn, the asset stays `failed`, and the 24h self-heal pass
re-bills it forever. On this box the two `20260723-bakin-logosvg-*` assets are
the live repro.

Root cause: `kindFor` in `plugins/assets/lib/enrichment/queue.ts` accepts any
`image/*` mime (and its own table lists BMP, which providers also reject), and
only the runtime engine runs the shared prep helper — the direct engine sends
raw file bytes.

### Decisions (interview)

- **D-A1 One vision-raster set + one conversion seam in `@bakin/core/media`.**
  Export `VISION_RASTER_MIMES` (png, jpeg, gif, webp) and replace all four
  copies: `plugins/chat/lib/routes.ts`, `plugins/chat/lib/channel-inbound.ts`,
  `src/core/conversation-turns.ts`, and the enrichment queue's `IMAGE_MIMES`.
  `prepareImageAttachment` (`packages/core/src/media/downscale.ts`) becomes
  the ONE "make this sendable" seam: raster under the cap → original;
  raster over the cap → downscaled JPEG (today's behavior); NON-raster image
  (SVG, BMP, TIFF, …) → rasterized PNG via sharp, bounded to the same
  1568px max dimension. Chat behavior is unchanged: SVG keeps riding the file
  lane (chat only ever passes raster types to the seam).
  The consolidation covers VISION ELIGIBILITY only: reuse the existing
  `packages/core/src/media/image-format.ts` (extension map +
  `mimeTypeForImagePath`) rather than adding a parallel table; serving,
  avatar and upload-allowlist policies stay where they are (chat web
  uploads keep rejecting SVG — `tests/plugins/chat/attachments.test.ts:95`).
  Codecs come from the pinned sharp build (jpeg, png, webp, gif, tiff, heif,
  svg, …; NOT bmp — verified by probe), so BMP lands in `unrasterizable`.
  Animated GIF/WebP and multipage TIFF send their FIRST frame/page;
  transparency is preserved (PNG output); SVG renders with sharp's default
  safe settings and a bounded density — input-size bound via sharp's
  `limitInputPixels`.
- **D-A2 The queue preps once; engines receive sendable files.** The queue
  calls the seam before the billed call and passes the prepared path/mime
  to `engine.run`; it owns cleanup after the last retry. The runtime engine
  drops its own prep/cleanup. Scanned-PDF pages go through the same seam per
  page. Result: the direct engine also gets downscaling for large images.
- **D-A3 Split terminal states by cause; nothing billed in either case.**
  The seam throws a typed `ImageNotSendableError { reason }` — callers branch
  on `reason`, never message text:
  - `sharp_unavailable` → `markEnrichmentFailed` with the `bakin install media`
    remediation. Free daily retry; heals once media is installed.
  - `unrasterizable` (sharp present, the codec is unsupported or the bytes
    don't decode) and `too_large` (still over the cap after downscale) →
    `markEnrichmentSkipped` with the reason. Filesystem errors (ENOSPC,
    EACCES on the temp dir) are NOT `unrasterizable` — they rethrow and
    record `failed`.
  - The queue's handling of these typed errors is explicit (status,
    counters, and the existing `AssetGoneError` race), not left to the outer
    catch that only logs.
- **D-A4 Skips are version-scoped.** `markEnrichmentSkipped` records
  `forVersion`; self-heal treats a skip with `forVersion < currentVersion`
  as stale and retries it, exactly like a stale `done`. A same-version skip
  is never retried by self-heal; an explicit force/backfill still runs it.

### Acceptance criteria

- An SVG asset enriches successfully from a rasterized PNG on both engines;
  the provider never receives `image/svg+xml`.
- BMP (no decoder in the pinned sharp) records `skipped` with the codec
  reason and makes zero provider calls.
- A scanned PDF whose page 2 fails preparation makes zero provider calls.
- Every preparation temp dir is removed on success, on each throw path,
  and after the last retry; originals are never removed.
- A skip on v1 is retried by self-heal once v2 exists.
- Without sharp: a non-raster image records `failed` with the install
  remediation and makes ZERO provider calls.
- A malformed SVG records `skipped` with a reason and is not re-enqueued by
  self-heal.
- The direct engine downscales a >2 MB raster (it sent raw bytes before).
- No file outside `packages/core/src/media/` declares its own raster mime list.
- After deploy, the two live logo SVGs enrich on the next self-heal pass
  (they are `failed`, so they are already in the retry set — no migration).

### Out of scope

- Chat rasterizing SVG into the image lane (stays file lane — deliberate).
- The search visual leg's own raster regex (`multimodal-search.md`) — a
  different consumer (antfly decodes bytes itself).

### Files

`plugins/chat/lib/{routes,channel-inbound}.ts`, `src/core/conversation-turns.ts`;

## B. #758 — team create/edit in a dialog

### Objective

The Manage Teams drawer (`plugins/team/components/team-manager.tsx`) expands
its create form inline and edits reporting through a per-row picker that
saves on change; team names cannot be edited anywhere. Make the drawer a
plain list and move entry into a focused, dismissible dialog.

### Decisions (interview)

- **D-B1 One `TeamFormDialog`, create + edit.** Create: name, ID
  (auto-derived from the name until touched), reports-to. Edit: name and
  reports-to; the ID is shown read-only (routing paths and `team:<id>`
  assignment tokens key on it). Rows get an Edit button; the inline
  reports-to picker is removed. Rename rides the existing
  `PUT /api/plugins/team/teams/:id` (no API change). "Add team" moves to the
  top of the Teams section.
- **D-B2 Dirty close goes through the kit guard.** `useUnsavedChangesGuard`
  (`@makinbakin/sdk/navigation`) owns Esc / Cancel / overlay / router
  navigation / unload while the form is dirty; the dialog's
  `onOpenChange(false)` calls `requestExit()`. Clean close just closes.
  Save errors render inside the dialog; delete errors stay on the drawer.
  Wiring per the guard contract: `onCancel` closes the dialog,
  `onSaveAndExit` catches failures and returns false, `guard.dialog` renders
  inside the form Dialog's nesting context, the Dialog is `busy` while
  saving (close icon + double-submit covered). "Stay" returns focus into
  the form; exit returns it to the Add/Edit trigger.
- **D-B3 Reports-to `null` means main.** `null` is the persisted
  main-agent sentinel (`plugins/team/lib/team-settings.ts:67`); the dialog
  shows it as the main agent, compares dirty state on the normalized value,
  and serializes it back as `null`. A reports-to agent that no longer exists
  shows as missing and must be re-picked before save.
- **D-B4 Rename gets real server validation.** `PUT teams/:id` assigns
  `body.label` unchecked today (`plugins/team/lib/routes/teams.ts:101`).
  Add a zod body schema: label a trimmed non-empty string, reportsTo
  string|null; 400 on anything else. The UI mirrors it.
- **D-B5 Draft baseline is captured once per opening.** Roster reloads while
  the dialog is open never reset the user's edits. After a successful save
  the dialog closes and reloads; a reload failure after a successful save
  shows the drawer alert (the change did land).

### UI conformance

- Pattern: `storybook/public/overlays/dialog.stories.tsx` — `ControlledFocusReturn`
  (external open state) + `NestedBehavior` (guard dialog over the form);
  `storybook/public/forms/unsaved-changes-dialog.stories.tsx` — `UnsavedExitDecision`.
- Contract: `@makinbakin/sdk/ui` (Dialog family, Field family, Form),
  `/patterns` (AgentSelect, ConfirmDialog, ListRows), `/navigation` (guard).
- Deviation: none expected. `bun run ui:conformance --quick` while iterating;
  `--full` before handoff.

### Acceptance criteria

- Add team opens a dialog; creating closes it, reloads the roster, and the
  new team appears in the list.
- Edit opens the same dialog prefilled; saving a new name or reports-to
  updates the row.
- Closing a dirty dialog (Esc, Cancel, overlay) shows the unsaved-changes
  decision; save / discard / stay all behave; a clean close shows nothing.
- Focus returns to the triggering button on close.
- Delete still confirms through `ConfirmDialog`.
- Create endpoint unchanged; PUT rejects empty/whitespace/non-string labels
  with 400.
- A team reporting to main edits its name without touching reports-to.

### Out of scope

Team ID renaming, editing the Global team, `useAgentStore.load()`'s
swallow-and-race behavior (noted; separate debt).

### Files

`plugins/team/components/team-manager.tsx`, new
`plugins/team/components/team-form-dialog.tsx`; new RTL test
`tests/plugins/team/team-manager.test.tsx`; `tests/plugins/team/ui-conformance.test.ts`
(pins `<AgentSelect>` in TeamManager at line 100 — update); the team
plugin browser fixture (`bun run test:ui`) for nested focus/dismissal;

or the team plugin knowledge doc (rename path), user docs if they describe

## C. #898 — health decisions verify, never trust a self-asserted file

### Threat model (stated honestly)

Agents run as the same OS user with shell access, and the HTTP API has no
authentication. Nothing here is a security boundary against a determined
same-user agent. The goal: every health, installer and consent decision
verifies real state instead of trusting a file an agent could write, and no
record claims more provenance than it has. The realistic failure is a
confused repair agent (the #898 incident forged a media receipt), not an
attacker.

Audit (2026-10-16, verified by Codex and by hand) found seven trust
points plus three adjacent ones. The owner's call: fix ALL of them in this
batch, one PR per concern, no new issues. Section C is the narrow PR;
D–I are the rest (designed below).

### C decisions

- **D-C1 Acks validate on read with the write rules.** One shared validator
  in `src/core/health-acks.ts` used by `writeAckRecord` AND `readAckRecords`:
  record key equals `incidentId`; `at` is a valid ISO time not in the
  future; `action_required` is snooze-only; snoozes carry a valid `until`
  with `0 < until − at ≤ 7 days`; `action_required` snoozes carry
  `evidenceSha`. A record that fails is dropped from suppression (the
  incident shows) and reported as an evidence gap on the projection — never
  a crash, never a silent reset of the other acks. No `actor` field (it
  would be self-asserted; see H).
- **D-C2 Repair requests are schema-validated per file.** A zod schema
  for `DoctorRepairRequest` in `src/core/doctor-repair-store.ts`; a
  malformed file is skipped and logged individually instead of aborting
  the whole listing. In `coveredIncidentIds`, an invalid or future
  `createdAt` covers nothing (checked before cooldown or column logic — no
  clamping). The legacy `kind`/`checkIds` reader defaults stay until
  #945 (margo still holds pre-#942 request files).
- **D-C3 Plugin runtime skills compare installed content.** In
  `src/core/onboarding/plugin-assets.ts`, scan and installer skip share ONE
  predicate: build the expected runtime skill (`buildRuntimeSkill`) and
  compare its files with what `runtime.skills.get` returns, instead of
  trusting the marker's `sha256`. `.userEdited` stays an overwrite lock,
  never evidence of conformity.
- **D-C4 The repair brief forbids silencing.** `src/core/doctor-delegate.ts`
  adds: never acknowledge or snooze an incident, never change doctor or
  escalation settings, never move the repair task to review to make it go
  quiet — report and block instead. Pinned by the brief's tests.
- Incidental: fix the stale `.onboarded` comment in
  `src/core/onboarding/state.ts:4-7` (the doctor runs every check without
  the marker).

### C acceptance criteria

- A hand-written permanent ack on an `action_required` incident, a snooze
  past 7 days, a future-dated ack, or an `action_required` snooze without
  `evidenceSha` does not suppress the incident; the projection reports the
  bad record.
- A future-dated repair request covers nothing; one malformed request file
  does not stop escalation from reading the others.
- A plugin skill whose installed content differs from the expected build
  reports drifted and is rewritten by the installer, even with a correct
  marker.
- The repair brief text carries the new rules.

### C files

`src/core/health-acks.ts`, `src/core/doctor-report-cache.ts` (evidence gap),
`src/core/doctor-repair-store.ts`, `src/core/doctor-escalation.ts`,
`src/core/onboarding/plugin-assets.ts`, `src/core/doctor-delegate.ts`,
`src/core/onboarding/state.ts`; tests beside each. Docs:
`.claude/knowledge/doctor-and-health-checks.md` (ack invariants),
`approvals.md` (coverage), `plugin-system.md` (skill verification).

## H. Approvals record honest provenance and refuse agent contexts

- **Problem:** `POST /api/approvals/:id/resolve` stamps the OS username
  (`packages/host/src/api/approvals.ts:54`) and `src/core/approvals/service.ts:136`
  hard-codes `type: 'human'`; workflow gate routes and Health apply resolve
  the same way. Records claim a human nobody verified.
- **D-H1 Provenance shape (direct format change, no backfill):**
  `{ channel: 'ui'|'cli'|'discord'|'mcp'|'runtime'|'hook', actor: { kind:
  'operator-declared'|'agent'|'channel-user'|'unknown', id? }, evidence:
  'declared'|'runtime-context'|'provider' }`. Evidence strength is set by
  the transport, never accepted from request JSON. Discord keeps its real
  user id and fail-closed approver allowlist.
- **D-H2 One guard before any `onResolve` side effect:** refuse when the
  actor is an agent, when the call carries a known agent context (MCP /
  exec-tool invocation context, CLI run-dir sidecar detected BEFORE `--as`
  is honored), or when the caller is unidentified. UI and CLI require an
  explicit operator declaration. Every entry point uses it: core resolve
  route, workflow gate routes + hooks, Health apply/confirm.
- **D-H3 Honest display:** decision surfaces say "Declared in UI",
  "CLI --as human", "Discord @user" — never "verified human".
- **D-H4 Transport (owner-confirmed 2026-10-18 after a Codex design
  review):** provenance is built server-side only. Browser decision clients
  send `X-Bakin-Operator: declared`; the server-rendered gate decision form
  posts the exact scalar field `operator=declared` (the one form exception —
  never a provenance object). Channel = `cli` when `X-Bakin-Origin: cli`,
  else `ui`. The CLI attaches `X-Bakin-Agent-Context: <agentId>` in the
  SHARED HTTP plumbing whenever it detects agent context, which overrides any
  declaration; it sends `X-Bakin-Operator` only with `--as human`. A
  malformed/empty agent-context header is refused, never read as "none".
- **D-H5 Agent-context detection (owner-confirmed):** Pi agent shells get
  `BAKIN_AGENT_CONTEXT=<agentId>` per command through the bash tool's
  `spawnHook` (never shared `process.env`); the CLI also treats a cwd inside
  a run dir (sidecar) or a registered agent workspace as agent context
  (OpenClaw cannot inject per-shell env). Detection runs before `--as`.
  In-process, every exec-tool invocation (MCP server + runtime exec
  provider) runs inside an AsyncLocalStorage agent-invocation context
  (`run`, never `enterWith`); any decision inside it is refused.
- **D-H6 One policy, every mutation boundary (Codex P1):** the refusal
  policy is one function used by `resolveApprovalWithResult` AND the Health
  direct-apply path for non-safe items (confirmed items need an operator
  declaration; safe auto-repairs are not operator approvals and are
  unaffected). The CLI needs `--as human` for decisions, including
  `bakin doctor --fix` on non-safe items (owner-confirmed). Refusals are a
  typed `ApprovalRefusedError` → 403 on every HTTP surface (incl. the HTML
  form and hooks' result, which carry a machine-readable code); MCP returns a
  tool error.
- **D-H7 Legacy records (Codex P2):** records with the old `actor` shape
  stay readable (status/decision/timestamps preserved) and display
  "Provenance unavailable — legacy record"; never inferred as declared.
- **D-H8 Display (owner-confirmed):** one formatter; provenance shows on the
  task activity/audit line for `approval.resolved` and in the Health repair
  request's events. Discord keeps its provider id.
- **D-H9 Bits companion (owner-confirmed):** messaging passes request-derived
  provenance to the gate hooks (no `'mark'` default), checks the hook's
  result BEFORE changing the deliverable, and agents can no longer approve
  WORKFLOW-BACKED deliverables even under `agentDeliverableApprovalPolicy:
  allowed` (bare deliverables unchanged; copy updated). Both repos raise
  their minimums and ship together.
- **Not attempted:** HTTP authentication; identifying an arbitrary shell
  `curl` or a shell that strips the markers (documented limit in
  `approvals.md`).
- **Acceptance:** an agent-context call with `--as human` is refused before
  side effects; a missing declaration fails; Discord unauthorized users
  fail; all entry points share the guard; records show declared provenance.

## G. Repair-task coverage is bounded and reuses the task

- **Problem:** `coveredIncidentIds` (`src/core/doctor-escalation.ts:57-66`)
  covers an incident forever while its repair task sits in review/blocked.
- **D-G1 (lean):** review/blocked coverage expires after the existing
  stale window. On expiry, escalation RESURFACES the existing task (one
  notification through the existing attention path, task link on the
  incident) — it never creates a duplicate. A repair task closed without
  the incident verifying healthy also resurfaces the same episode. Moving a
  task between columns does not reset the window.
- **D-G2:** the incident carries its repair task id in the report
  projection and the incident card links it through the existing
  resource-link pattern (no association exists today —
  `packages/sdk/src/types/health.ts:395`).
- **D-G3 Resurface mechanics (owner-confirmed 2026-10-19: "re-announce +
  reopen"):** window W = `doctor.escalationStaleAfterMs` (12h), measured
  from the request's last `resurfaced` event, else its `createdAt` — column
  moves never reset it. Per request whose incidents are still FRESH
  action_required in this cycle's report:
  - task missing → not covered (a new request may open — unchanged);
  - task closed and the request `verified` → not covered (recurrence is a
    new episode);
  - task closed, NOT verified → resurface `closed-unfixed`;
  - task open, inside W → covered; past W → resurface `stale`.
  Resurface = (1) an in-flight run on the task → skip this cycle (still
  covered; the agent is working); (2) a task outside review/blocked moves to
  **Review** through ONE core verb (`escalateTaskToReview`) — the documented
  Health-escalation exception to the agent transition table (todo/done →
  review are otherwise refused) — with a task log line saying why;
  (3) the request carries a pending approval → re-announce it (re-publish
  `approval.pending`; no duplicate channel card); a delegated request has
  none → a `health-navigate` approval opens on the SAME task (Dismiss =
  7-day snooze, like every navigate incident) so every resurfaced task
  rides the one approvals attention path; (4) append a `resurfaced` event
  (the window mark). The incidents stay covered — never a new task.
  Review hardening (Codex round 1): cycles are serialized; every resurface
  re-reads the request and task and re-judges them before mutating (auto-
  close may have verified it); an `applying` request always covers and never
  resurfaces; a task leaving Done reopens through the audited
  `reopenIfLeavingDone` (the completion row is cleared); a Blocked task
  keeps its column and reason; attaching sets `sent` only over
  `completed`/`failed`; `doctor --delegate` is serialized and returns
  `already_delegated` for incidents an open repair task works (a deleted
  task works nothing). Round 2: the resurface re-read, re-judge and writes
  are ONE synchronous block. Round 3: dispatch re-reads the column right
  after its claim (a task resurfaced to Review mid-gate is released, never
  moved back); auto-close withdraws the approval on the updated request;
  the open-work index ignores future-dated requests. Round 4: an invalid
  or future `resurfaced` mark is ignored (never extends cover); the index
  keeps every candidate so delegation falls back past a deleted task; the report link reads a memoized
  incident→request index the store invalidates on every write.
- **Not attempted:** a new awaiting-operator state or reminder UI.
- **Acceptance (fake clock):** expiry, restart, repeated column moves,
  concurrent cycles, closed-but-unfixed tasks; stable task id; one
  notification per window; an in-flight run is never yanked.

## I. Upgrade consent never trusts the lock file

- **D-I1:** `requiresConsent = target declares any bins OR permissions`,
  from the validated target manifest alone (`src/core/plugins/upgrade-gate.ts:218-262`).
  The lock-derived "widening" baseline and its helpers are deleted; the
  response carries the full declaration (`declaredPermissions`,
  `declaredBins`) and CLI/UI disclose everything, unchanged entries
  included. Lock entries stay inventory/cleanup only.
- **Acceptance:** a forged lock entry cannot remove the prompt; unchanged
  declarations still prompt; a changed target invalidates acceptance;
  empty declarations need no consent; rejection mutates nothing.

## D. Archive binaries verify against a manifest pin

- **D-D1:** `archive: { format: 'tar.gz', member, extractedSha256 }`
  REQUIRED in `packages/core/src/plugins/bin-requirement.ts`. ONE
  `verifyInstalledBin(target, requirement)` hashes the real bytes against
  the manifest pin (raw or extracted); markers are bookkeeping, never
  integrity. Callers: installer skip (`bin-installer.ts`), plugin-assets
  scan, sync-scanner (its duplicate rule deleted), capability-readiness bin
  leg (was existence-only). The installer verifies archive AND member
  before running `verifyArgs` or committing. An invalid manifest is a
  visible finding, not "no bins".
- **D-D2 Rollout:** the Bits PR (terminal plugin, ocr + transcribe packs)
  adds `extractedSha256` computed from freshly downloaded, archive-verified
  members and bumps versions; it merges first; the three are reinstalled
  on each box under current Bakin; then Bakin's strict check ships.
- **Acceptance:** a forged binary with a matching forged marker fails all
  four callers; a wrong extracted pin prevents execution; an old installed
  manifest shows invalid, never green.

## F. npm payloads prove their dependencies resolve

- **D-F1:** new `src/core/agent-packages/npm-verify.ts` —
  `verifyNpmPayload` checks the generated manifest, the copied payload
  scripts, each direct dependency's installed name + exact version
  (resolution anchored in the payload, no ancestor/global fallback,
  scoped/ESM/exports-map safe), and declared entry files. Used by
  installer reuse, post-install staging verification and readiness. No
  imports, subprocesses or network per doctor run. Wording: "dependencies
  resolved at declared versions", never "integrity verified".
- **Acceptance:** empty `node_modules`, wrong version/name, missing entry,
  ancestor fallback, altered payload script all fail; a valid payload
  reuses offline.

## E. Model files are hashed before any skip (lean)

- **D-E1:** a shared streaming-hash helper in `packages/core/src/integrity/`
  (reuses the download primitive's hashing; knows nothing about packs or
  antfly). Capability-pack model reuse (`requirements-installer.ts:185-190`)
  and antfly search-model install skip (`packages/adapter-antfly/src/models.ts:187-195`)
  always stream-hash against pins before skipping; a post-pull mismatch
  (`models.ts:243`) FAILS instead of warning; tokenizer entries get pins
  (`model-pins.ts:38`); the indefinite size/mtime digest cache stops being

  antfly enumerates its own files.
- **Not attempted:** background periodic verification.
- **Acceptance:** same-size corruption defeats the installer skip; a
  post-pull mismatch fails the install; doctor wording never claims
