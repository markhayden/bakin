## Overview

Eight PRs in a fixed order. Two commit kinds, declared per commit:
- **prep** — additive under the current contract, fully tested, and either (a) **active** (it changes behaviour on its own, e.g. an owner slice that repoints its incidents to a new repair action under the old contract) or (b) **unactivated** (modules, tools, UI components and handlers that nothing calls yet; declared `[unactivated]` in the commit title so the reviewer knows the tree is green AND unchanged in behaviour);
- **cutover** — ONE commit that flips a contract or an engine: types, zod mirrors, every producer, every consumer, persisted-record handling, fixtures, pins, public-API regeneration. No shims (D9), so a cutover is large; it is reviewed as one unit against the inventory tables and reverted as one unit.

Every PR: branch in the main checkout (never merge-to-test), Codex ≥2 rounds (cap ~5, stop at approve, findings fixed in-batch), green CI, Mark's live test on 3737 (recipe stated per PR), squash-merge. One release at the end; margo's upgrade (operator-run, spec §3.6) is the acceptance test.

## Architecture Decisions (spec, restated for the implementer)

- **Prep is active or declared unactivated; cutovers are atomic (R1 #1, R2 B1).** An owner slice may repoint incidents to a new action UNDER THE OLD CONTRACT (`type: 'repair'`, `safety` stamped) — that is active prep; the planner (`doctor-repair.ts:179`) only invokes actions referenced by repair resolutions, so repointing is what makes them reachable. Type deletions, new required fields and engine swaps happen only in a cutover.
- **Prerequisite matrix (R1 #2, R2 B2):** updater fetch-at-sha + reinstall + sync operations → PR1 prep. `core.diagnose` apply delegates through the EXISTING lane until PR5's cutover. Search resilience (PR2) and the coordinator (PR3) precede the engine (PR5). CLI agent mode (PR4) precedes the engine so the brief advertises behaviour that exists; `--yes` on plugin upgrade / package sync / reinstall is refused `consent-unreviewed` until PR6 writes records (asserted in PR4, success asserted in PR6). Basic pending-restart surfaces live in PR3; PR7 adds the automatic-update toggle. Settling before PR7 closes on boot + one full sweep (max 10 min); PR7 adds convergence as a further condition. Update all excludes the Bakin subject until PR7. PR7's commands precede its pipeline test.
- **Frozen approvals (R2 B1 1.6):** PR1's cutover is the first incompatible change to the health-repair proposal schema; it RETIRES pending legacy health approvals raw in the same commit (bounded raw reader, cancel via the approval path with a raw fallback, channel edit best-effort + audit row). PR5's supersede handles tasks and stores and re-runs retirement for approvals the adapted old engine opened in between (readable under the new schema).
- **Two resolution types, one mode policy, one authorization gate (D1, D2).** `repairMode` / `authorizeMutation` in `packages/core/src/health/`; row 158 is `widensAuthorization: true` (one-click).
- **Declared incident catalogs (R2 B10, R3 N5):** a check registers `incidents: HealthIncidentDeclaration[]` where a declaration is a FINITE family — `{ id, subjectKind, resolution: { type: 'repair', actionId } | { type: 'human', needs }, required: 'always' | 'never' | 'owner-decides' }` (e.g. `not-ready` for `not-ready:<capability>`, `schema-error` for `schema-<wf>-<n>`); an emitted incident carries `declarationId` plus its runtime `key`; registration validates every declaration's references (action registered or in `SHARED_ENGINE_ACTIONS = ['core.diagnose']`, `needs` present) and FAILS the owner's activation on error; runtime hrefs are validated at emission by the existing same-origin rule; the runner validates an emitted instance against its declaration's resolution kind / action id / needs (and the existing runtime schema for the rest) — never key literals, no template language, no second copy of runtime resolutions. A row with split variants declares one family per variant.
- **Every Health apply passes the gate from PR1 on (R3 N2):** `doctor-repair.ts`'s apply path calls `authorizeMutation` for every item regardless of caller (old escalation, click, agent tool); until consent records exist (PR6) a `system`/`agent` actor on an upgrade/sync/reinstall mutation is refused `consent-unreviewed`, which the old engine treats as "needs the operator" (one-click approval), never as a failed attempt. So no upgrade-shaped mutation is ever automatic before PR6, and PR1's owner slices may stamp those actions `manual` (operator path) without relying on classification alone.
- **Upgrade-shaped repairs are owned by the updates record (spec D7; R2 B6):** `plugin-upgrade`, `plugin-reinstall`, `package-sync`, `package-reinstall`, `search-engine-install`, models install run through ONE `startSubjectMutation(subject, mutation, actor)` (PR6 slice) that admits one equivalent mutation, counts failures once on the shared `(subject, action, failureIdentity)` key, applies `authorizeMutation`, and reports the terminal outcome to both the Health subject record and the update record.
- **Fallback authority (R2 B4, R3 N4, R4 R4.2):** the fallback brief carries a `handbackToken` (HMAC of `taskId:runSeq`, signed with the persisted signing key — introduced in 5.6 and reused by consent records in 6.1 — single-use per hand-back, 24 h TTL); `bakin_exec_health_handback` and `bakin_exec_health_repair` require the token AND require the calling principal to be the fallback task's assignee; `tasks_complete` refuses a FALLBACK TASK (keyed by task id) without an accepted hand-back. Per transport: **Pi** — the per-turn exec-tool provider is created with `{ runId, taskId }`, so the tools additionally require the bound run to be the fallback run, and `tasks_create` is refused inside it (a stolen token from another Pi run is refused). **OpenClaw** — the MCP credential is agent-scoped and no per-run carrier exists, so NO fallback lane runs on OpenClaw in this initiative (Mark, 2026-10-23, Open Question 4): `core.diagnose` on an OpenClaw install hands back to the operator immediately (`handed-back`, reason `no-agent-lane-on-runtime`, default operator actions, no agent turn); the fallback tools refuse any OpenClaw principal; a follow-up issue proposes a dedicated `repair` system runtime agent with its own MCP credential. The window rule is therefore not needed.
- **Maintenance admission (R2 B5):** phases staging → admission → resources; restart-class work is started by `withMaintenanceAdmission(service, start)` so admission is taken before any resource; chat starts and queued continuations are gated at `turns.ts:305` (messages retained, resumed after defer/cancel); a Terminal that is active but registers no hook blocks on ANY running session until the operator overrides; agents submit restart-class verbs asynchronously (CLI in agent mode returns the operation id).
- **Notification occurrence identity (R2 B7, R3 N7):** the subject record keeps a persisted `occurrence` counter per `(subject, action)` that increments when the action re-enters a red state after having cleared (observation ids are stable `${checkId}:${key}` and are not changed for this); the event id `<subject>:<action>:<state>:<occurrence>` is shared by the browser toast key, the Discord row and History; a resolved subject's Discord link opens `/health?history=<eventId>`, which the History tab resolves to the retained entry; onboarding seeds `server.publicUrl` from the host name.
- **Consent records** are signed with the persisted signing key (`~/.bakin/signing-key`, 0600, created once in 5.6 and shared with hand-back tokens). **The first upgrade is performed by the new binary**; `release.json` carries `rollbackSafeFrom`; the pipeline proves the span in the recovery direction. **Scope stays narrow** (one fallback budget, no store-wide versioning, no Discord threads, no universal draft serialization, supersede only Health-owned tasks, sweep scoped to retired identifiers).

## Commit Strategy (batch rules)

One conventional commit per slice. Gate before EVERY commit, each step on its exit status: `bun run typecheck && bun run lint` + the slice's named test files `--isolate` (named per commit below; "pooled" lists are not accepted). Per PR before the live test: `bun run check:cycles && bun run lint:home-bypasses && bun run test` (alone), `bun run build:host && bun run build:plugins && bun run ui:conformance --quick` (`--full` at every merge-ready checkpoint with UI), affected plugin `test:ui` fixtures with their `test-results/bakin-ui/index.html` report inspected, `bun run docs:check`, `bun run ui:public-api:check` — **regeneration happens inside the commit that changes a public contract** (PR1 1.5 optional `incidents` + 1.7 required; PR2 2.5 `PluginManifest.data`; PR3 3.1 `OperationWaitingFor`, 3.3 navigation registry hook; PR5 5.1 subject types; PR6 6.4; PR7 7.6 if the header hook signature changes), with the reason in the body; `ui:performance` without regeneration (moved ceiling → D0.8, Mark decides). Restore `packages/sdk/styles.css` before suites/commits; never commit `generated-version.ts`. Revert sets are computed from real dependencies and listed per commit; "alone" means "while this commit is the tip" — once a later commit consumes it, it reverts with that consumer set. UI work composes existing public patterns (`ListRow`/`ListRowGroup` `Grouped`, `ConfirmDialog` `CanonicalUsage`, `OperationProgress` `Waiting`/`RepairWithChildren`, `PluginSettingsRenderer` `CompactListComposition`/`HighlightedField`, `UnsavedChangesDialog` `UnsavedExitDecision`, `Banner`, `StatusBadge`, `CodeBlock`) through the focused SDK entrypoints (`HeaderBar` is a local shell component, not a public pattern — the update/restart bar composes `Banner`); a new pattern needs the conformance skill's deviation approval. Every PR ends with a `docs(knowledge)` commit.
