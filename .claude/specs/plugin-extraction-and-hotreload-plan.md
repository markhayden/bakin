# Execution Plan — Plugin Architecture v2: Extraction + Hot-Reload

Companion to `.claude/specs/plugin-extraction-and-hotreload.md`. Read the spec first for the *what* and *why*; this is the *how* — exact files, signatures, dependency graph, per-checkpoint verification, rollback story.

## Refresher

**Eight phases, eight separate PRs.** Each phase ships independently and leaves the codebase shippable. Phases 0-2 are deep technical work in bakin itself (foundations, monorepo install, link + hot-reload). Phase 3 is repo creation outside bakin (no bakin PR needed). Phases 4-7 are sequenced application work.

**State of main on plan creation:**

- **Plugin lifecycle (#170 / #142 / #119) is solid.** `bakin plugins {install, upgrade, remove, list, scaffold}` all exist. Tarball backup, consent prompts, registry teardown sweeps. Lockfile at `~/.bakin/plugins/lock.json`. Confirmed by `src/core/cli.ts:136-336` and `packages/core/src/plugins/lockfile.ts`.
- **Source parser** lives at `src/core/plugins/upgrade.ts:353-368` (`githubCloneUrl()`) AND a mirror at `packages/host/src/api/plugins/install.ts:234`. Both need the `#subpath` extension. The comment at upgrade.ts:350 explicitly notes "Mirror of the parsing in `install.ts`" — we maintain both.
- **Teardown surfaces are comprehensive.** `src/lib/plugin-registry.ts:526-528` already calls:
  - `unregisterPluginNodeTypes(pluginId)` — workflow node types
  - `unregisterPluginNotificationChannels(pluginId)` — notification channels
  - `unregisterPluginHealthChecks(pluginId)` — doctor checks
  - Plus `HookRegistry.unregisterByPlugin(pluginId)` — hooks
  - Plus `removeExecToolsByPlugin(pluginId)` — MCP exec tools (`scripts/lib/registry.ts:56`)
  - Plus `purgeContentType(name)` — search tables (per #119)
- **`buildUserPlugin`** lives at `packages/host/src/plugin-host/user-plugin-builder.ts:122`. Takes a plugin directory path; runs `Bun.build` + optional `bun install`. Foundational for both install AND link.
- **`PluginHost.tsx`** (client-side loader) at `packages/host/src/plugin-host/PluginHost.tsx`. On mount it fetches `/api/plugins/manifest`, then dynamic-imports each plugin's `clientEntry`. Each plugin module runs `registerPlugin` on load. The browser-global registry holds nav + slot data.
- **Embedded assets** generated by `scripts/generate-embedded-assets.ts` → `packages/host/src/api/_embedded-assets-static.ts`. Lines 41-42 reference `plugins/projects/dist/{client,index}.js`; lines 55-56 reference `plugins/messaging/dist/{client,index}.js`. Routes 85-86 + 99-100 expose them as `/api/plugins/{messaging,projects}/assets/*.js`. Auto-regenerated during full build.
- **Dev loop infrastructure** at `scripts/dev.ts`. Uses chokidar; per-plugin watcher at line 287; inflight + pending coalescing at lines 122-136; SSE broadcast for `dev:reload` / `dev:error` / `dev:recover` at lines 140-158. Server-side rebuild **explicitly bails on `index.ts` changes** (line 296-299) — that's exactly what Phase 2 builds.
- **`CORE_PLUGINS` constant** at `scripts/dev.ts:29` lists all 10 plugins including messaging + projects. Phase 4-5 trim to 8.
- **`bakin.config.ts`** lists all 10 plugins as `{ path: 'plugins/<id>' }` entries. Phase 4-5 trim to 8.
- **Onboarding state machine** at `src/core/onboarding/index.ts:68` (`COMPONENT_ORDER`) lists 8 components. Phase 6 adds `recommended-plugins` as the 9th.
- **Onboarded marker** at `~/.bakin/.onboarded` (`src/core/onboarding/state.ts`). Doctor gates on this. Phase 6 must NOT re-prompt for plugins on subsequent `bakin onboard` runs against an already-onboarded machine.
- **Plugin file inventories:**
  - `plugins/messaging/`: 23 source files (manifest + types + constants + index + client + 11 components + 1 hook + 5 lib files + package.json + tests + dist, dropping dist).
  - `plugins/projects/`: 13 source files (manifest + types + index + client + 6 components + 2 lib files + package.json + tests + dist).
- **Antfly content types:**
  - `messaging` registers `messaging_brainstorm` table (index.ts:249). Plugin id and table name preserved post-extraction → no migration.
  - `projects` registers `projects` table (index.ts:83). Same.
- **Top-level side effect audit (preview for Phase 0):**
  - `messaging`: zero top-level `setInterval`/`setTimeout`/`process.on`/`fs.watch`. The single `setTimeout` match is at `components/planning-layout.tsx:118` inside a callback — UI side, fine. Plugin has `onShutdown()` at index.ts:1346.
  - `projects`: zero matches. Plugin has `onShutdown()` at index.ts:836.
  - **Both plugins are clean.** Phase 0 audit is a confirmation pass, not a fix pass.

**Per-phase verification adds `bunx tsc --noEmit -p tsconfig.app.json`** alongside `bun test --isolate` — Bun's runtime test runner doesn't catch TS-only errors that CI does.

## Rollback Story

**Per-PR rollback** is the primary safety net.
- Phase 0: trivial (audit + tests).
- Phase 1: revert leaves install/upgrade flows on the existing source-string format. Lockfile schema additions are back-compat (extra fields ignored on read).
- Phase 2: largest blast radius. Full revert disables `bakin plugins link` + hot-reload. Existing install/upgrade still works. Linked plugins in user lockfile become orphaned entries (no harm, but `bakin plugins list` may show oddly until they're cleaned up).
- Phase 3: revert = delete bakin-bits-official repo (or empty it). No bakin impact.
- Phase 4-5: revert in bakin restores messaging/projects to source. The bakin-bits-official side stays — those plugins are still publishable, just bakin no longer extracts them. Slightly weird state but recoverable.
- Phase 6: revert removes the prompt step from `bakin onboard`. No effect on installed plugins.
- Phase 7: revert removes lint rule. Imports still work.

**Branch rollback (mid-flight):** `git checkout main && git branch -D feat/plugin-extraction-phase-N`. Phases 0-2 are atomic; phases 4-5 are paired (bakin + bakin-bits-official). Roll back the bakin side first; the bakin-bits-official side is harmless on its own.

**Data migration:** none required across the full series. Plugin id → settings.json path → Antfly table all preserved through extraction. User lockfile ([`~/.bakin/plugins/lock.json`]) gains `linked` field in Phase 2 (back-compat: optional).

**The dangerous mistake to avoid:** breaking the source-string format. The lockfile records source strings; if Phase 1 ships a regex that accepts new formats but the parser doesn't handle them, lockfile reads will fail silently.  Solution: schema validation on lockfile load + migration script if format ever changes.

## Open Micro-Decisions (settle during build)

These are small enough to not need spec-level interview but worth flagging:

- **Where the version-stamp registry lives.** Best home is per-plugin `state` object in `pluginRegistry.state[pluginId]` — already tracks per-plugin metadata. Add `version: number` field there. Decision: yes, single source.

- **Does `bakin plugins link` accept relative paths?** Default: resolve against `process.cwd()` and store absolute in lockfile. User can `cd ~/dev/bakin-bits-official && bakin plugins link plugins/messaging` and it just works.

- **Auto-link UX for "alongside-cloned" repos.** Skip for v1 per spec. If we want it later, scan for `bakin-bits-official` siblings of `process.cwd()` during dev start, prompt to link. Don't auto-link silently.

- **Hot-reload coordinator runs in core process or dev process?** Core process — that's where the plugin runtime lives. The watcher needs to call into the registry teardown sweep and the activate cycle. Both live in core. `scripts/dev.ts` continues to coordinate the host-shell + SDK rebuild pipeline; the plugin coordinator is separate.

- **What happens if a linked plugin's source dir is deleted from disk while bakin is running?** Symlink becomes broken. Watcher fires an `unlink` event. Coordinator should treat this as "plugin removed" — sweep registries, log warning, remove lockfile entry. User explicitly running `bakin plugins unlink` is the same code path.

- **What if a user runs `bakin plugins install <id>` while the same id is currently linked?** Refuse with clear error: `plugin "<id>" is currently linked from <localPath>; run "bakin plugins unlink <id>" first`.

- **Versioning convention reaffirmed.** `<plugin>-v<semver>` git tag style. `messaging-v1.0.0`, `projects-v0.1.0`. Tags live in bakin-bits-official. Plugin's `bakin-plugin.json#version` matches the tag's semver portion. Same convention for agent packages later.

- **`@bakin/eslint-config-plugin` package shape.** Ships from bakin's `packages/eslint-plugin-bakin-plugin-author/`. Plugin authors install with `bun add -D @bakin/eslint-config-plugin` and extend in their config. Already accounted for in Phase 2 C11.

- **The "bakin onboard --yes" behavior with the new prompt.** Auto-accept defaultSelected:true entries. Skip prompt entirely. Confirmed in Phase 6 acceptance.

- **Templates + scaffolding interaction.** `bakin plugins scaffold <name>` (already exists) should produce a plugin shape ready to drop into `bakin-bits-official/plugins/<name>/`. Confirm the scaffold output matches the bakin-bits-official template in Phase 3.

## Notes for the Build Phase

- **Run `bun test --isolate` after every commit.** Don't batch — catches regressions while context is fresh.
- **Don't reformat unrelated code.** Mechanical changes only. Resist drive-by cleanups.
- **Type-check is non-negotiable.** `bunx tsc --noEmit -p tsconfig.app.json` after each commit.
- **The plugin host is fragile.** Phase 2 touches `PluginHost.tsx`, `_adapter.ts`, the plugin-registry teardown surfaces. Each commit should leave the registry in a consistent state. If a commit breaks the runtime invariant ("either old or new plugin is registered, never both, never neither"), something's wrong with the sequence.
- **Cross-cutting save scenarios.** Test C10 covers this. Manual verification: open both `index.ts` and `client.tsx` of the fixture, change a route response shape AND the component that consumes it, save both at once, observe page UI updates within 1s with no transient error state.
- **CI parallelism.** Phase 2 is the longest CI job (lint rule package adds tests; integration test is heavy). Consider splitting CI workflows so plugin-author lint package CI is its own job.
- **bakin-bits-official CI coordination.** Phase 3 launches CI before bakin's @bakin/sdk version may have shipped. Pin to a placeholder version initially; bump to real version once Phase 4 starts.
- **Manual sanity testing before each merge.** Spin up a real bakin instance, hit the install/link/onboard flows. Don't trust CI alone for this work — there's significant human UX surface.
- **Commit messages.** Conventional commits. Scope by phase + concern: `feat(plugins): ...`, `chore(onboarding): ...`, `docs(arch): ...`.
- **PR template.** Always link the spec + plan + relevant issue (#174, #175). Include manual smoke results in PR description.
- **After all phases.** Verify `gh issue close 175` happens after Phase 2. Verify `gh issue view 174` is referenced in Phase 7 (close if architectural inversion is now resolved; otherwise leave open).
