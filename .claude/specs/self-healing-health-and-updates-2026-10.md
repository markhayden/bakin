## 1. Objective

Every Bakin release has broken margo (the one production box) in a way its operator could not fix from the UI and its agents could not fix at all. rc.42 did it again on 2026-10-23: zero incidents at 14:13, six at 14:25:54, all caused by the upgrade, none with a button, one of them impossible without a restart that no surface offered. The agent lane blocked itself on a `Continue? [y/N]` prompt and re-blocked when requeued.

The goal is a platform where:

1. **Most things heal themselves.** The engine runs every repair it knows how to run, unattended, as soon as the condition is observed, bounded by two honest axes (does it delete user content, does it spend money).
2. **What cannot self-heal is one click.** The remaining repairs run under the operator's name from one button in Health (and from Explore/Team/the header where the subject lives), never from a text recipe.
3. **What truly needs a human says exactly what it needs.** A credential, a payment, a judgement call: the card names the field and links to it. Nothing else may be red.
4. **Upgrades keep the install whole.** Plugins, packages, search models and the engine upgrade on their own when the source is trusted and nothing new is being consented to; Bakin itself can, behind a toggle, after a pre-swap compatibility check, and always converges its companions after a restart.
5. **Agents are the fallback diagnosticians, not the first responders**, working in a Terminal session the operator can watch and take over, with a CLI that never prompts them.

Users: Mark (operator of margo and the dev box). This machine is the only user; no backwards compatibility, no shims, no one-shot migrations.

## 3. Design

### 3.1 Incident contract (SDK, `packages/sdk/src/types/health.ts`)

```ts
export type HealthSubjectKind = 'plugin' | 'package' | 'hub-skill' | 'service' | 'agent' | 'table' | 'runtime' | 'channel' | 'setting' | 'record' | 'task' | 'system'  // `record` = an asset, brand, workflow, spend-policy or other owned record (plan amendment, 2026-10-23)
export interface HealthSubject { kind: HealthSubjectKind; id: string; label?: string }

export type HealthHumanNeed = 'credential' | 'payment' | 'decision' | 'external-install'

export type HealthResolution =
  | { type: 'repair'; key: string; label: string; actionId: string }
  | { type: 'human'; key: string; label: string; needs: HealthHumanNeed; href: string; field?: string }

export interface HealthIncidentBaseInput {
  key: string
  title: string
  impact: string
  class?: HealthIncidentClass
  /** REQUIRED: what this incident is about. One card per subject in the report. */
  subject: HealthSubject
  /** Other affected resources (unchanged shape). */
  resources?: HealthResource[]
  resolution: HealthResolution
  /** This incident is a symptom of another subject's failure; the report folds it under that owner ONLY when the owner's repair declares it resolves this incident key (D7, Codex r1 #7). */
  dependsOn?: { subject: HealthSubject; resolvedBy: string /* owner action id */ }
}
```

A subject card on the wire carries `actions: HealthSubjectAction[]` — every independent unresolved resolution for that subject (one subject may need a repair AND a credential at once); each action has its own state (§3.3). Folding never hides an action: a dependent incident folds only when its `dependsOn.resolvedBy` names the owner's running/queued repair, and it is re-verified after that repair; if it survives, it unfolds as its own action.

Core registers ONE engine-owned repair action every owner may reference for repair-shaped incidents it cannot fix deterministically: `core.diagnose` (effects all false) — applying it is the fallback lane (§3.4). So "a repair-shaped incident with no action" does not exist: the author chooses `core.diagnose` explicitly, and the registration rule "actionId must resolve" holds for every incident.

Rules enforced at registration (`src/core/doctor-checks.ts`) and by an architecture test:
- A `human` resolution requires `needs`; `href` must be a same-origin path; `field` is the settings/form field id when the fix is a value to enter.
- A `repair` resolution must reference a registered action (owner-namespaced) — a dangling `actionId` fails registration.
- No incident type may carry free-text steps. Copyable commands are gone from incidents; the CLI prints the equivalent `bakin` verb for a one-click when run from a terminal (`bakin doctor` already lists repairs).
- A transient state (engine warming, first sample, inspection could not run) is an observation with `status: 'unknown' | 'warning'` and `snapshot` metadata; the check's `maxAgeMs` re-runs it. Health lists such observations under the check, not as cards. The report's `unknown_stale` status still covers evidence gaps. **Bound (Codex r1 #5, r2 #10, r3 #8):** an INSPECTION that keeps failing — observation `unknown` (could not run, timed out, unreadable) for 3 consecutive sweeps or 90 minutes, whichever is sooner — becomes an incident on the check's subject with resolution `core.diagnose`. A known advisory or warning state (unsupported platform, an unused broken workflow, usage anomalies) stays what it is; only "we cannot see" escalates.

### 3.2 Repair actions and the ONE mode policy

```ts
export interface HealthRepairEffects {
  deletesUserContent: boolean
  spendsMoney: boolean
  /** Consents to new permissions/bins/secrets/npm payloads, or changes spend, routing or policy — always one-click (Codex r1 #1). */
  widensAuthorization: boolean
  /** The action restarts a supervised service or Bakin; the engine serializes these behind the restart gate (§3.7). */
  restartsService?: 'search-engine' | 'bakin' | 'runtime'
  /** Incident keys on dependent subjects this repair resolves (drives folding, §3.1). */
  resolves?: string[]
}
export interface HealthRepairActionDefinition { id; label; effects: HealthRepairEffects; plan(target, report); apply(items, op) }
export type HealthRepairMode = 'self-heal' | 'one-click'
export function repairMode(effects: HealthRepairEffects): HealthRepairMode  // packages/core/src/health/repair-mode.ts — the only place that decides

// ONE authorization gate for every mutation path (auto-apply, convergence, Health repair, CLI --yes, agent, operator click):
export function authorizeMutation(input: { subject; mutation: 'upgrade' | 'sync' | 'reinstall' | 'restart' | 'rebuild' | 'delete' | 'policy'; source?: string; consentDelta?: ConsentDelta; actor: 'system' | 'agent' | 'operator' }): { allowed: boolean; reason?: AuthorizationRefusal }  // packages/core/src/health/authorize-mutation.ts
```

Per-item effects remain possible (`repair-store` purging trash: the planner stamps `effects` per plan item; the mode is judged per item, so the dir-creation item self-heals while the purge waits for the click).

**One gate, every path (Codex r1 #1).** `authorizeMutation` is called by the auto-apply pass, by `convergeInstall`, by every Health repair apply (system or click), by the CLI before honouring `--yes`, and by the agent exec tools. Its rules: `system`/`agent` actors may upgrade/sync/reinstall only from a trusted source with an empty consent delta and a reviewed consent record (§3.6); hub skills are never permitted for `system`/`agent`; `delete`/`policy` and any non-empty delta require `operator`; `restart`/`rebuild` need no authorization beyond the restart gate. A refusal names its reason, and every surface renders it with the SAME copy, control and transition (Codex r2 #7):

| Reason | Copy | Control | Transition |
|---|---|---|---|
| `consent-delta` | "Needs your OK: asks for <n> new permission(s)/binary/secret" | Update button → delta-first dialog with "Allow once" and "Trust this source" | waiting-for-operator |
| `consent-unreviewed` | "Review its declaration first" | link to the Review installed declarations card | waiting-for-operator |
| `declined` | "You declined automatic updates for this" | Update button (one-time) · "Allow automatic again" | waiting-for-operator; attention per the §3.3 rule (quiet while the subject works, red when it is required and broken — a repair after decline is always a click) |
| `untrusted-source` | "Not a trusted source — updates stay manual" | Update button · "Trust this source" (adds to `trustedSources`) | waiting-for-operator |
| `hub-skill` | "Hub skills are always reviewed" | Update button (trust gate re-runs) | waiting-for-operator |
| `operator-only` | "Deletes content / changes spend — confirm" | ConfirmDialog (health-repair approval) | waiting-for-operator |
| `quarantined` | "This release failed here on <date>" | Retry this release anyway · Roll back · containment | handed-back |

"Allow once" consents to this identity only; "Trust this source" is the permanent list change and says so. `skipped` hides a row; it never blocks a repair — convergence or a repair may still install a skipped identity when the installation is otherwise broken (stranded), and the preview says so. An operator click carries the operator header (#898) exactly as today.

The `health-repair` approval kind survives for one-click items (delete/spend): the button opens the ConfirmDialog, the confirm resolves the approval under the operator header, and the apply runs as the same child operation. There is no other approval kind in Health.

### 3.3 The repair engine (replaces `doctor-escalation.ts`, `doctor-delegate.ts`, the navigate/operator-review parts of `doctor-approvals.ts`; `doctor-reservations.ts` semantics kept)

**Unit of state = one ACTION on one SUBJECT.** A subject card carries every unresolved action; each action has its own state, verification, attempt budget and admission. The durable record is `~/.bakin/doctor/subjects.json` (zod, replaced wholesale on write).

```
observed ──(mode self-heal)──▶ fixing(attempt 1) ──verified──▶ healed (the action disappears when its declared outcomes re-evaluate healthy)
   │                              │fail
   │                              ▼ wait 5 min
   │                          fixing(attempt 2) ──fail──▶ failed ──▶ fallback (core.diagnose, §3.4) ──▶ handed-back (RED, outcome attached)
   │                                                           └──(fallback task not dispatched within 10 min)──▶ handed-back (RED, "fallback could not start")
   ├──(mode one-click | human | expected authorization refusal)──▶ waiting-for-operator (RED iff the attention rule says so)
   ├──(containment accepted)──▶ contained (neutral, limitation shown; returns to observed when a new eligible identity verifies)
   └──(any running state, no progress past the operations stuck clock, or a readiness wait past its bound)──▶ stalled (RED, operation link)
```

- **Verification is per action (Codex r2 #9, r3 #6):** an attempt is `verified` when the originating observations the action's repair declares it `resolves` re-evaluate healthy on a fresh targeted run, plus that action's own functional probe where one exists (plugin: activated + its own health check; search engine: canary query; models: files verified; Bakin: new bootId serving + first sweep). Other unmet requirements on the same subject (a missing credential) are their own actions and never fail this one. Quarantine (§3.6) happens only when the evidence implicates the installed identity itself (activation failure, its own check failing after the install), never because a sibling action is unresolved.
- **Expected authorization refusals are not failures (r2 #7):** `consent-delta`, `consent-unreviewed`, `declined`, `untrusted-source`, `hub-skill`, `operator-only` move the action to `waiting-for-operator` without consuming an attempt or opening a fallback.
- **Retry and recurrence (r3 #7):** two engine attempts five minutes apart, counted per `(actionId, failure identity)` where the failure identity is built from stable cause/target fields (error code, subject, target path/identity), never from timestamps or message text. The budget persists across restarts and across the card disappearing; it resets only after **24 continuous healthy hours** for that action, measured from the start of the healthy interval.
- **Readiness bounds:** process readiness 2 min; functional verification 5 min after the operation succeeds; progress = the operations clocks (an operation that keeps reporting progress is never `stalled`, however long it runs — margo's reindex took 7 minutes); no overall completion deadline for progressing work.
- **Settling window (D8, r2 #10, r3 #8):** after boot or a self-update, self-heal JUDGEMENT (attempt counting, fallback, red for repairs) waits until `convergeInstall()` (§3.7) settles and one full sweep completes after it, minimum 3 min, maximum 10 min. Independent checks start immediately; checks whose subject the convergence is repairing show `fixing` with the convergence operation linked. The window never suppresses a human-only action (badge + toast + Discord apply from the first sweep). Past 10 min the window closes; progressing work stays `fixing`, stalled work goes red.
- **Admission** keeps the reservation model (#896 D3.2) and attaches a click only to an EQUIVALENT running request (same action, same target, same requested mutation); anything else waits visibly.
- **Auto-close** of the fallback task: unchanged judgement (fresh healthy evaluation of the action's originating checks), with the recurrence budget retained (above).
- **Cron:** `doctor.intervalMs` stays; `doctor.escalation*` keys are deleted; `doctor.repair = { enabled: true, retryDelayMs: 300000, maxAttempts: 2 }` replaces them.

**The ONE attention rule (r3 #9).** Red (badge, toast, Discord) requires an unresolved OPERATOR action on a REQUIRED capability. Everything else is neutral and visible in Health:

| Situation | Card | Badge/toast/Discord |
|---|---|---|
| self-heal queued/running/progressing | Fixing (operation link) | no |
| human need (credential/payment/decision/external) on a capability something uses | action row with field/button | yes, from first observation, settling or not |
| one-click repair pending (delete/spend/widen) on a required capability | button | yes |
| optional update available (manual-only source, declined subject, untrusted source) while the installation WORKS | quiet row + reason chip | no |
| the same subject BROKEN (its check fails) | the repair action is red regardless of declined/untrusted — the row says why automatic is off | yes |
| handed-back / stalled / fallback could not start | red with default actions | yes |
| contained (operator accepted containment) | neutral "Contained — not fixed", limitation listed, auto-resume noted | no |
| watch / advisory | listed | no |

"Required capability" = the subject is referenced by something that runs (a plugin that is installed and enabled, a pack whose capability an agent declares, the search engine when search is enabled, a schedule's workflow); the owner check supplies the fact. `skipped` (an update identity the operator hid) and `disabled` (a kind switched off in Settings) affect UNATTENDED upgrades only: a REPAIR of a broken subject may still install the skipped/disabled identity when that is the only fix, and the preview says so. `declined` means "nothing unattended for this subject, ever": its repair is offered as a one-click (red when required and broken), never run on its own (Codex r4 B2). Containment accepted by the operator holds until they lift it or until a newer eligible identity verifies, whichever first; a manual disable/pause made afterwards is respected (no auto-resume over it).

### 3.4 Fallback agent lane (D3)

- **Trigger:** an action in `failed` after two engine attempts, or an incident whose resolution is `core.diagnose` (plugin activation threw, a check crashed, ledger unreadable, an inspection failed past its bound).
- **One task, one budget (Codex r3 #4):** ONE task per subject, assigned to main, `source.purpose: 'fallback-repair'`, column todo, kicked immediately. Budget = **3 agent turns in total**; every turn counts (the first dispatch, a requeue by the operator, the turn that reads an asynchronous repair's result). When the budget ends without an accepted hand-back, core settles the task itself: it completes the task with the default outcome (`handed-back`, reason `no-valid-handback`, raw log attached) and supplies the default operator actions (Retry the engine repair, the subject's containment, Open logs). When verification succeeds at any point — including after the last turn submitted asynchronous work — core closes the task as repaired. No sub-delegation (the exec tool refuses `tasks_create` from a fallback run).
- **Terminal:** when `bakin_exec_terminal_session` is available to main, the brief instructs it to create a session titled `Health repair: <subject>` linked to the task and run every command there, leaving it open for the operator; otherwise its own shell.
- **Asynchronous repairs (r1 #6, r3 #2):** the agent never waits on restart-class or long repairs. It submits them through `bakin_exec_health_repair` (starts the operation, returns the id) and ENDS its turn; when the operation settles, core re-dispatches the task (if budget remains) with the verified outcome in the brief, or settles the task itself (if not). The maintenance coordinator (§3.12) therefore never waits on an agent's own turn.
- **The brief** carries: the subject and its actions; the failed engine attempts with operation outcomes and log excerpts; the hand-back tool's schema with one valid example per kind; the registered actions the agent may propose for this subject; the sanctioned CLI verbs (§3.5); the Terminal convention; the turn budget and how many remain; the rule that `bakin_exec_tasks_complete` refuses a fallback task without an accepted hand-back and returns the schema.
- **Hand-back contract (r1 #4):** submitted through `bakin_exec_health_handback`, validated by core, ONE of: (a) `proposal` — a registered action id + target the engine can plan now (an unplannable proposal is rejected back to the agent while turns remain) → one-click "Apply <label>" with the agent's reasoning as detail; (b) `human` — a `HealthHumanNeed` with the exact field/href → the human action; (c) `upstream-blocked` — evidence plus a containment the engine offers as one-click (disable the plugin, pause the capability, pause the schedule) with what it stops and the note that it resumes automatically when a new eligible identity verifies; rendered "Contained — not fixed", never as healed. Free text alone is not a hand-back.
- **Re-open guard:** no new fallback task for a subject within 12 h of a hand-back unless the operator presses Retry (engine repair first, re-dispatch only if that fails again).
- Terminal is a Bits plugin: core feature-detects the exec tool through the registry; no core import.
- **Runtime scope (plan amendment, 2026-10-23):** the agent lane runs on Pi, where a turn's tool calls are bound to its run. On OpenClaw the MCP credential is agent-scoped and shared with chats, so no sub-delegation refusal can be enforced per run; there `core.diagnose` hands back to the operator immediately (red card, default actions, no agent turn). A dedicated `repair` system runtime agent with its own credential is a follow-up.

### 3.5 CLI agent mode (D3)

`src/cli/identity.ts` already knows when an agent runs the CLI (`BAKIN_AGENT_CONTEXT`, run-dir sidecar). In agent mode:
- Every prompt helper (`promptUpgradeConsent`, `readYesNo`, `promptYesNo`, `confirmPrompt`, skills `confirm`) refuses immediately with exit code 2 and one line: `non-interactive: pass --yes to accept <what>` — never waits on stdin. All prompt helpers also gain the TTY guard for humans piping output.
- `--yes` is honoured for the **sanctioned repair set**: `plugins upgrade <id>` (only when the consent delta is empty; otherwise exit 3 `needs operator consent: <delta>`), `packages sync`, `agents sync`, `install {search,search-models,media,plugin-assets,agent-sync,capabilities}`, `reindex` (repair mode only, never `--force`), `doctor --fix` (self-heal items only), `search:stats`, `check *`.
- Refused in agent mode regardless of flags (403/exit 3): approvals, `updates apply`, `update`, `search:reset`, `plugins remove|install`, `packages remove`, `skills install`, anything with `--as human`. Today only approvals, `updates apply`, `update` and non-safe repair apply are refused; the plugin install/remove, package remove and hub-skill install refusals are NEW (`src/cli/commands/plugins.ts:290`, `packages/host/src/api/plugins/remove.ts:56`, `packages/host/src/api/packages/dynamic.ts:87`, `packages/host/src/api/skills.ts:213` — Codex r1 correction) and go through `authorizeMutation`.

### 3.6 Updates engine, consent records, auto-apply (D4, D5, D11)

**Records.** `UpdateRecord` gains:
```ts
consentDelta?: { permissions: string[]; bins: string[]; secrets: string[]; npm: string[] }   // empty object = no new consent needed
autoApply?: { eligible: boolean; reason?: 'disabled' | 'untrusted-source' | 'consent-delta' | 'consent-unreviewed' | 'declined' | 'quarantined' | 'skipped' | 'turn-in-flight' | 'restart-pending' | 'preflight-failed' | 'hub-skill'; scheduledAt?: string; lastAttempt?: UpdateAttempt }
quarantined?: { identity: UpdateIdentity; reason: string; at: string }
```
`UpdateAction.manual` is deleted. Every non-current, non-unsupported record carries an `operation` action or is `blocked` with a reason that names the subject's owner (a linked dev plugin stays `unsupported`).

**Sources.**
- `package`: observe the remote even when the installed manifest is unreadable; **fetch and validate the manifest at the RECORDED commit first (Codex r1 #8)** — valid upstream bytes at the same commit → `update-available` reason `repair` with a same-commit reinstall operation; remote moved to a valid manifest → `update-available` reason `repair`/`newer-commit`; upstream invalid at both → `blocked: upstream ships an invalid manifest` with an `upstream-blocked` containment action. Same-version new-sha from a trusted git source is `update-available` reason `newer-commit` (auto-eligible).
- `hub-skill`: operation action that re-runs the trust gate + reinstall; never auto-eligible.
- `plugin`, `search-engine`, `search-models`, `bakin`: unchanged observation; records gain the delta and eligibility.
- `gateway`: stays informational (`blocked` with the runtime's own upgrade verb) — it is not Bakin's to apply.

**Apply.** `src/core/updates/apply.ts` gains `case 'package'` (a `packageSyncOperation(lockKey|agentId, { expected: { sha }, reinstall: true })` exported from the packages/agent-packages routes, the updater accepting `expected` and `reinstall` so a same-commit reinstall re-projects from the staged manifest) and `case 'hub-skill'`. "Update all" = every applicable record with an empty delta, started as one parent operation with one child per subject (same shape as a Health repair). **Every apply previews its consequences (Codex r1 #12):** the dialog (Health, Explore, Team) and the CLI confirmation list the included subjects with versions and source, the impacts (`server-restart`, `search-interruption`, `reindex`, `download` with bytes), the excluded rows with their reasons, and — for a delta — the new permissions/bins/secrets as the focused content ABOVE the consequences, never instead of them. Partial success is per child: the parent reports each child's outcome, the records re-observe individually, and the surfaces render the same parent/child view. A batch that includes a restart-class child acquires maintenance admission (§3.12) for the whole batch before starting, so a child never waits on its own parent.

**Consent record and the first-upgrade bootstrap (Codex r1 #10, r2 #4, r3 #3).** Nothing signs a consent record out of an old lockfile. On the first boot of this release every installed plugin/pack/hub skill has no record: the updates engine marks them `autoApply.reason: 'consent-unreviewed'`, every row shows a button, and Health → Updates shows ONE persistent "Review installed declarations" card (no repeated toasts; one Discord message on that first boot). The card lists each subject's full permissions/bins/secrets/npm (an unparseable local declaration is shown from the staged upstream manifest at the recorded commit — the bytes a repair would install; if that fails too, the row offers containment). **Order: preview first, consent last.** "Review and apply" builds the COMPLETE preview — the repairs those declarations would authorize (pending pack syncs, plugin upgrades with empty delta), their consequences (downloads with bytes, restarts, reindex), and the exclusions (untrusted sources, hub skills) with reasons — and only the final confirmation of that preview writes the consent records (bound to the reviewed manifest shas) and admits the batch. Cancelling the preview writes nothing: the subjects stay unreviewed. There is no "accept without applying" choice (Codex r4 C3): consent that exists is consent the auto-apply pass will act on, so the only ways out of the card are "Review and apply" (confirmed preview) and "Review later" (everything stays a button, nothing is signed). Per-subject "Decline" marks the subject `declined` (works as installed, never auto-updates, quiet chip while it works, re-asked only when its declaration changes). A later visit shows what changed since the review. Convergence on that first boot upgrades nothing unattended (§9.10); zero-touch applies from the second upgrade (§9.7). `~/.bakin/plugins/consents.json` (plugins) and the package lock entry (`consent` field) hold `{ manifestSha, permissions, binNames, secretSlots, npmPayloads, signedAt, signature }`, signed with the consent-token HMAC secret, written on every install/upgrade commit that passed consent. The gate (`gateUpgradeConsent`) keeps "the lockfile is never the baseline" for the HUMAN path; the AUTO path requires a valid signature AND a trusted source AND an empty delta, else it yields to the button. A bin whose name is unchanged but whose sha moved is NOT a delta (Q1); a new bin name, permission, secret slot or npm payload is. Git-subpath installs from a trusted repo follow the same rules as artifact installs (Q5), bound to the observed commit sha; linked dev installs stay unsupported.

**Trusted identities.** `updates.trustedSources` governs plugin/package/hub-skill sources; Bakin releases, the search engine and the model set are trusted by construction — their pins (release repo `github:markhayden/bakin`, the antfly release host, the model digests) are compiled into the binary and verified by checksum/signature, so `authorizeMutation` treats them as trusted without a list entry.

**Auto-apply pass.** After each observation pass the engine runs `autoApplyPass()`: for each record `authorizeMutation` allows for actor `system` (kind switch on, trusted source, empty delta, reviewed consent record, not skipped, not quarantined, no in-flight agent turn touching the subject, for plugins no live Terminal session owned by that plugin), start the subject's operation with `origin: 'system'` and `expected` bound to the observed identity, serialized, two at a time at most, with the same re-observe-on-success watch and the functional verification of §3.3. Failures record `autoApply.lastAttempt` and back off like observations; after two failures the subject becomes a one-click with the error as detail (and feeds the Health subject record, §3.3). The Bakin kind additionally requires the preflight (§3.7) and the restart gate.

**Recovery contract (Codex r1 #3, r2 #2/#3, r3 #1).** A functional-verification failure that implicates the installed identity QUARANTINES it on the record (automation never reinstalls it). The contract is honest about what the PREVIOUS release can do:

- **The first upgrade (rc.42 → this release) is performed BY the new binary, never by rc.42's updater (Codex r4 C2, r5 #1/#2).** rc.42's updater has no preflight hook, no `rollback` verb and no restart watcher, and it would install whatever its update record points at — so it is not used. The release notes carry the procedure and this release's acceptance (§9.11) tests it end to end on a fixture home: (1) download this release's binary to a temp path and verify its checksum; (2) `<new> preflight --home ~/.bakin --json` — reports strandings, confirms rc.42 is inside this release's `rollbackSafeFrom` (it MUST be — a release-pipeline test), and writes `~/.bakin/recovery/preflight.json` with the preflighted artifact's sha; (3) `<new> install-self --home ~/.bakin` — refuses unless its own sha matches `preflight.json` (the binary that was checked is the binary that installs; a newer release that appeared meanwhile is never substituted), copies the running rc.42 binary to `~/.bakin/recovery/bakin-rc42` and the lock/settings snapshot + the per-plugin `data.schemaVersion` the lock records to `~/.bakin/recovery/companions.json`, swaps itself in, and `launchctl kickstart`s the service; from here the new binary's convergence, watcher and rollback apply. **Recovery to rc.42** (automatic by the watcher if the new binary does not serve, or `<new> rollback --to rc42` by hand): restore the rc.42 binary and the pre-upgrade lock/settings snapshot, and CONTAIN every companion rc.42 cannot be shown to run safely — any plugin whose recorded `data.schemaVersion` advanced during the new release's tenure or is undeclared is moved, plugin dir AND `plugin-data/<id>`, into `~/.bakin/recovery/<ts>/contained/` (rc.42's loader never sees it; nothing is deleted; the data is kept for the forward path), and the rollback prints the contained list. rc.42 then runs without those plugins; reinstalling one from rc.42's own repair starts it with fresh data by design — old code never reads newer or unknown-schema data. The §9.11 fixture covers changed AND undeclared plugin schemas with writes in between, and a release that advanced between preflight and install (refused). Everything below applies to upgrades performed BY this release or later.
- **Unattended Bakin updates require a declared rollback-safe span, in the RIGHT direction (Codex r4 C1).** `release.yml` publishes `release.json` beside the binaries: `{ version, rollbackSafeFrom: '<oldest previous version that can still READ AND WRITE every store, lock, settings file and companion record AFTER this release has written to them>' }` — i.e. this release makes only backward-compatible changes to on-disk state relative to that version. The preflight compares the installed version with `rollbackSafeFrom`: inside the span, the update may apply unattended and roll back automatically; outside it (the release changes a store in a way the previous binary cannot handle), the update is button-only and the dialog says "cannot be rolled back automatically — stores change". The release pipeline enforces the declaration with a test that upgrades a fixture home, WRITES through the new binary (a task, a usage scan, a settings save, a plugin upgrade), rolls back to `rollbackSafeFrom`, and verifies the old binary reads and writes cleanly. No store-wide versioning subsystem is added.
- **Bakin checkpoint** = the previous binary at `<binary>.previous` (one slot, retained until the next verified Bakin identity replaces it) + a snapshot of `~/.bakin/{settings.json, plugins/lock.json, packages/lock.json, updates.json}` + the staged companion set. **Automatic rollback** fires only when the update was inside the `rollbackSafeFrom` span (recorded in `recovery/companions.json` at swap time) and the new binary does not serve within the restart bound (Codex r5 #4): a detached watcher process (`bakin restart-watch`, spawned by the updating binary before the swap, outliving the old server) swaps `.previous` back, restores the snapshot files (the overwritten current ones are kept beside as `*.rolled-back-from`), reinstalls the recorded companion set from the retained checkpoint, and restarts; the span check above guarantees the old binary reads the stores. Offline path: `<binary>.previous rollback` (this release and later implement it) — it reads the same recorded span and refuses an out-of-span rollback unless `--force-incompatible-stores` is passed, naming the stores. An out-of-span update (manually approved, button-only) that fails to serve is NOT rolled back by the watcher: the new binary stays, the subject is `stalled` (red) and the card carries the manual command with the store warning. Rollback failure → `stalled` red with the manual path in the card.
- **Plugins:** the replace-transaction backup is retained THROUGH activation and functional verification (today retired at commit — `replace-transaction.ts:478` moves); activation/verification failure rolls back automatically through it. Plugin data is never rolled back: a plugin manifest may declare `data.schemaVersion`; the lock records the highest version written; a rollback is allowed to ACTIVATE the previous version only when both sides declare a version and the target's is ≥ the recorded one — a lower version OR a missing declaration on either side is unknown compatibility and the subject is contained (restored on disk, not activated) with the operator's choice to activate anyway (Codex r4 C1).
- **Packs / hub skills:** previous lock entry + projections; rollback = sync to the recorded previous commit; quarantine + button (no automatic rollback); agent edits outside managed blocks untouched.
- **Search engine:** previous binary; rollback = reinstall it + repair reindex (content untouched); quarantine + button. **Search models:** previous files retained until verified; rollback restores them.
- **Quarantine always has a way forward (r2 #3):** "Retry this release anyway" (one explicit attempt of the exact identity), "Roll back" only when the previous identity is eligible (compatible contract/`bakinRange`, checkpoint present, data-version rule above), otherwise the subject's containment with its consequences; the record keeps observing and a newer eligible identity re-enables automatic apply.

**Settings.** `updates: { enabled, intervalMs, autoApply: { bakin, plugins, packages, searchModels, searchEngine }, trustedSources: string[] }` with D11 defaults (no quiet-hours key — Q2). UI: Settings → System & Alerts → "Updates" section (five switches, trusted-source list editor); the header update bar gets the "Keep Bakin updated automatically" toggle bound to `autoApply.bakin`.

**Surfaces.** Health → Updates: per-row Update button for every operation action (packages and hub skills included), an "Update all" button in the tab header, an "Automatic" chip on rows the engine will apply (with `scheduledAt`), an "Automatic — blocked: <reason>" chip when `authorizeMutation` refuses, the delta rendered as the consent dialog's focused content above the consequences, a "Restart pending — waiting for <blocker>" row with "Restart now" / "Defer 1 h" when a Bakin update is swapped but not restarted (Codex r1 #11; the same state in the header bar and `bakin updates`), and a History section (§3.11). ### 3.7 Self-update: pre-swap preflight and convergence (D5)

- **Preflight stage** (new, between `verify` and `prepare-restart`): the downloaded binary runs `bakin preflight --home <home> --json` (new hidden subcommand; read-only; exits 0/1) which, with the NEW code's schemas, reports every installed plugin (artifact compatibility via the index, manifest parse) and package/hub skill (manifest parse under the new schema, upstream availability of a fix). **"Fix available" means a specific companion release that is verified AND installable under current authorization (Codex r1 #2):** the preflight resolves the exact companion identity, checks trust + consent delta through `authorizeMutation`, downloads and verifies it into staging BEFORE the swap. The auto path refuses (`preflight_failed`, button + list) when any companion is missing, untrusted, or needs a decision; the human path shows the same list and collects the needed consents in the same dialog before the swap. Convergence then installs the staged companions, never fetches blind.
- **Convergence operation** `convergeInstall(reason: 'boot' | 'post-update')`, started from startup recovery CONCURRENTLY with the doctor (independent checks run from boot; checks whose subject convergence is repairing show `fixing` with the operation linked; the settling window of §3.3 only defers self-heal judgement) — Codex r4 B1: (1) search engine pin: stop old, **wait for port release (poll up to 30 s)**, start new, repair reindex if the data dir was cleared; (2) plugins: upgrade every stranded plugin with an empty delta, list the rest as one-click; (3) packages/hub skills: sync every record whose installed manifest fails the current schema or whose fix was recorded by the preflight; (4) re-initialize adapters whose init failed (3.8); (5) one full doctor sweep after it settles (the sweep that closes the settling window). Idempotent; owns `install-state` then `search-engine`; shows in the tray; audited.
- The release guard (`scripts/check-plugin-contract.ts`) extends to pack manifests: a change to the pack manifest schema is refused until every official Bits pack at the pinned Bits commit parses under it (the #1004 class of break becomes impossible to release).
- **Restart gate (Q2):** every restart-class action goes through the maintenance coordinator (§3.12). No time window.

### 3.8 Search adapter resilience

- `initialize()` failure is not sticky: the adapter schedules re-initialization (5 s, 15 s, 60 s, then every 5 min) and `available()` re-probes; a successful `bakin install search` (in-process or via the server) calls `search.initialize()` again.
- `assertServicePortsReleased` polls for up to 30 s before concluding a foreign listener holds the port; `restartService` never leaves the unit unloaded (a failed start re-runs `ensureProvisioned`, and on repeated failure the unit is bootstrapped from the plist on disk).
- The wedge watchdog starts its progress clock at engine readiness (not Bakin boot), treats table creation as progress, and never bounces within 5 minutes of an engine start.
- The outbox pump drains immediately on an engine `unavailable → available` transition (evidence item 8; to be confirmed in code).
- Health: `engine-unavailable` becomes a repair (`search-engine-restart`, effects `restartsService: 'search-engine'`) whose second attempt is `bakin install search`; `binary-missing`/`service-unprovisioned` become the install repair; `service-ownership` stays human (`decision`).

### 3.12 Maintenance admission (restart-class work — Codex r1 #6/#11, r2 #1/#8, r3 #2/#10)

One **maintenance coordinator** in core owns admission for restart-class work. Blockers are SERVICE-SPECIFIC:
- **Search engine restart:** blocked only by a running search operation that is not an ancestor of the requester (reindex/reset/install) — queries already degrade honestly through the budget and the outbox, so turns and tabs never gate it (the watchdog restarts the engine today without any gating).
- **Bakin restart:** blocked by in-flight agent turns; running operations that are neither ancestors of the requester nor waiting on maintenance; Terminal sessions with a live foreground process OTHER than the requester's own follower (a CLI that started the operation identifies itself by operation id and is never its own blocker — r3 #2); browser tabs that answered the last `restart-poll` as `dirty` within 10 s (unanswered, hidden/sleeping or disconnected tabs count as clean) — and any tab KNOWN to be `saving`, which stays a blocker until its save settles or the operator overrides, even if it disconnects meanwhile: silence never proves a save finished (Codex r4 B3; bounded by the 1 h rule).
- **Requests coalesce only when identical** (same mutation on the same target); a batch acquires admission once for its restart-class children; the Bakin child of a batch runs LAST, the parent persists every other child's outcome before the swap, and the convergence after restart reports the batch complete with those recorded outcomes (durable continuation — no re-run). Downloads and staging happen BEFORE admission is requested.
- **Hold, then drain:** while a request is pending, NEW dispatches and new operations on the same service are held (`waitingFor: 'maintenance'`) EXCEPT children an already-running (draining) operation needs to finish; admission is granted as soon as blockers drain, and is taken BEFORE the operation acquires `install-state`/`search-engine`.
- **Agents never block synchronously:** every agent/CLI submission of restart-class work is asynchronous (operation id returned, follower optional), so no agent turn waits on admission that waits on that turn.
- **Bounds and controls:** pending > 1 h → one-click with every blocker NAMED (tab page + last seen, Terminal session title, agent + task); "Defer 1 h" releases the hold and re-arms with "Resume now"; "Restart now" overrides tabs and foreground processes (named in the confirm), never an in-flight agent turn; cancel/timeout releases the hold. The pending state shows in the header bar, Health → Updates and `bakin updates`.
- **Edits are not lost (r3 #10):** this rides the public dirty-state/navigation contract, not a new serialization scheme — a dirty page stays mounted across the reconnect (no forced reload), a known `saving` tab is a blocker until its save settles (disconnecting does not clear it), a save whose result the restart made uncertain is re-fetched and reconciled before the page reports it saved, and the reconnect shows a "Bakin restarted" banner. Sleeping tabs that could not receive `restart-imminent` lose nothing because nothing was reloaded.
- Tests: parent/child batch with a Bakin child (ordering + continuation); two simultaneous restart requests; the requester's own Terminal foreground command; a draining operation that needs a child; a dirty tab that goes silent; a `saving` tab; defer → resume; the fallback agent submitting a restart and ending its turn.

## 7. Testing strategy

- **Policy units:** `repairMode`, consent delta, auto-apply eligibility (every `reason`), settling window, retry schedule, subject grouping, badge projection — pure functions, table-driven.
- **Architecture tests:** no `instructions`/`rerun`/`navigate` literals in incident producers; every registered action declares `effects`; every incident's `actionId` resolves; no `manual` update action; `selfUpdate(` still has one caller; no `doctor-escalation`/`delegate` imports remain.
- **Registration teeth:** a fixture plugin registering an incident with a dangling action or a `human` resolution without `needs` fails activation.
- **Engine integration:** fake sources + fake operations drive the state machine through fixing → healed, fixing×2 → failed → fallback task → handed-back; settling window gating; admission under a concurrent UI click.
- **Search resilience:** fake `ServiceIo` with a port that frees after N polls (boot race), a restart whose start fails once (unit never left unloaded), a wedge clock that ignores TableNotFound; adapter re-initialization after a failed init.
- **CLI agent mode:** spawn the CLI with `BAKIN_AGENT_CONTEXT` and stdin `ignore` for every prompting command: exits 2 with the flag hint, never hangs (bounded by `--timeout`).
- **Recovery:** a plugin whose new release fails activation is quarantined and rolled back through the transaction backup (retained through verification); a Bakin binary that fails to serve within the bound is rolled back by the detached watcher; `<binary>.previous rollback` works when the new binary cannot execute; a quarantined identity is never auto-applied again, "Retry this release anyway" runs it once, rollback is offered only when eligible, containment otherwise; a store newer than the rolled-back binary is refused fail-closed and shown as containment.
- **Maintenance:** the six cases listed in §3.12.
