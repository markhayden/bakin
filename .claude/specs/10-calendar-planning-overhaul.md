# Phase 10: Calendar Planning Overhaul

**Status:** Spec only — not yet implemented
**Dependencies:** Calendar plugin v2 (current), Team plugin (OpenClaw adapter)

## Problem

The calendar plugin's brainstorm interface is a stateless chat widget. Messages live in React state and vanish on navigation. There is no persistent record of planning conversations, no way to iteratively refine individual content items, no streaming feedback while the agent thinks, and no way to manually edit agent-proposed content. Channels are hardcoded to Discord. The result is a planning tool you can't plan with — every session starts from zero, bulk regeneration replaces targeted refinement, and there's no audit trail of *why* content decisions were made.

## Goals

1. **Persistent planning sessions** — conversations saved to disk, resumable, browsable
2. **Streaming responses** — see tokens arrive in real-time, future-proofed for tool-use transparency
3. **Review panel with two-stage approval** — soft-confirm individual items during planning, then commit the full plan to the calendar
4. **Manual editing** — edit any field of a proposed or calendar item from the drawer
5. **Configurable channels** — optional multi-channel tags on content items, filterable on calendar views
6. **Multi-agent future-proofing** — single-agent sessions now, but data model supports expanding later
7. **Full MCP + CLI coverage** — every new endpoint gets a corresponding exec tool and CLI command

## Phase 1: Planning Sessions (Persistence Layer)

### Data Model

New type `PlanningSession`:

```typescript
interface PlanningSession {
  id: string                          // 8-char hex via crypto.getRandomValues (same pattern as plugins/tasks/lib/ids.ts)
  agentId: string                     // single agent per session
  title: string                       // auto-generated from first message, editable
  status: 'active' | 'completed'     // completed when plan is confirmed or manually ended
  createdAt: string                   // ISO
  updatedAt: string                   // ISO
  messages: SessionMessage[]
  proposals: ProposedItem[]           // flattened list of all proposed items across messages
}

interface SessionMessage {
  id: string
  role: 'user' | 'assistant'
  content: string                     // agent narrative text (no JSON blocks)
  timestamp: string
  proposalIds?: string[]              // links to proposals generated by this message
}

interface ProposedItem {
  id: string                          // stable ID for tracking across revisions
  messageId: string                   // which message generated this
  revision: number                    // increments on agent revision
  agentId: string                     // defaults to session agent; supports future multi-agent
  title: string
  scheduledAt: string
  contentType: string
  tone: string
  brief: string
  channels?: string[]                 // optional distribution channels
  status: 'proposed' | 'approved' | 'rejected' | 'revised'
  calendarItemId?: string             // set when committed to calendar
  rejectionNote?: string              // why it was rejected (fed back to agent)
}
```

### Storage

- Directory: `~/.bakin/calendar/sessions/`
- One JSON file per session: `{sessionId}.json`
- Index not needed — list by reading directory, sort by `updatedAt`
- Sessions are append-friendly: messages and proposals only grow (no in-place mutation of message content)

### API Routes

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/sessions` | List sessions (returns id, agentId, title, status, updatedAt, proposal counts) |
| `GET` | `/sessions/:id` | Full session with messages and proposals |
| `POST` | `/sessions` | Create new session (agentId required, title optional) |
| `PUT` | `/sessions/:id` | Update session metadata (title, status) |
| `DELETE` | `/sessions/:id` | Delete session |
| `POST` | `/sessions/:id/messages` | Send message (triggers agent response) — replaces `/brainstorm` |
| `PUT` | `/sessions/:id/proposals/:proposalId` | Update proposal (approve, reject, edit fields) |
| `POST` | `/sessions/:id/confirm` | Confirm plan — creates CalendarItems for all approved proposals, marks session completed |

### MCP Exec Tools

Every session endpoint gets a corresponding exec tool so agents can interact with planning sessions programmatically:

| Tool Name | Description | Key Params |
|-----------|-------------|------------|
| `bakin_exec_calendar_session_list` | List planning sessions | `status?` (active/completed), `agentId?` |
| `bakin_exec_calendar_session_get` | Get full session with messages + proposals | `sessionId` |
| `bakin_exec_calendar_session_create` | Create a new planning session | `agentId`, `title?` |
| `bakin_exec_calendar_session_update` | Update session metadata | `sessionId`, `title?`, `status?` |
| `bakin_exec_calendar_session_delete` | Delete a session | `sessionId` |
| `bakin_exec_calendar_session_message` | Add a message to a session (triggers agent response) | `sessionId`, `message` |
| `bakin_exec_calendar_proposal_update` | Update a proposal (approve, reject, edit) | `sessionId`, `proposalId`, `status?`, `title?`, `brief?`, `tone?`, `scheduledAt?`, `channels?`, `rejectionNote?` |
| `bakin_exec_calendar_session_confirm` | Confirm plan — commit approved proposals to calendar | `sessionId` |

Note: `session_message` via MCP is non-streaming — it makes the full OpenClaw call and returns the complete response. Streaming is a UI concern; agents calling this tool get the same result synchronously.

## Phase 2: Streaming Chat + Conversational Context

### Server: Streaming Endpoint

Replace the blocking brainstorm endpoint with a streaming one:

**`POST /sessions/:id/messages`** returns `text/event-stream`:

```
event: token
data: {"text": "Great idea! "}

event: token
data: {"text": "Here's what I'm thinking..."}

event: proposals
data: [{"id": "p1", "title": "...", ...}]

event: done
data: {"messageId": "msg_abc"}
```

Implementation:
1. Load session from disk (full message history)
2. Build system prompt with agent persona + planning instructions
3. Send full conversation history as messages array to OpenClaw gateway with `stream: true`
4. Pipe SSE chunks back to client, accumulating the full response
5. On stream end, parse proposals from the accumulated response
6. Append message + proposals to session file
7. Send final `proposals` event with parsed items, then `done`

The real OpenClaw gateway **confirmed supports streaming** (standard OpenAI SSE format: `choices[0].delta.content` chunks, `data: [DONE]` terminator). The Imitation Crab mock does NOT support streaming yet — `dev/imitation-crab/gateway.ts` needs a streaming upgrade so `npm run dev:mock` works with this feature. For dev mode fallback: detect non-streaming response and wrap in a single SSE sequence (one `token` event with full text + `proposals` + `done`). This keeps the client code identical either way.

**Imitation Crab streaming upgrade** (add to PR 2 scope):
- Modify `dev/imitation-crab/gateway.ts` `/v1/chat/completions` handler
- When request body contains `stream: true`, return `text/event-stream` with chunked `delta.content` events
- End with `data: [DONE]`

### Conversational Context

The key fix: the agent receives the **full session history** as proper chat messages, not flattened into a single prompt. This means:

```typescript
const messages = [
  { role: 'system', content: systemPrompt },  // persona + planning instructions
  ...session.messages.map(m => ({ role: m.role, content: m.content })),
  { role: 'user', content: newMessage },
]
```

The system prompt includes:
- Agent persona (from `~/.openclaw/` workspace)
- Planning instructions (propose items as JSON, revise specific items when asked, etc.)
- Current proposal state: which items are approved, rejected, or still proposed — so the agent knows the "state of the board"

### System Prompt: Targeted Revision Instructions

Critical addition to the system prompt to solve the "regenerates everything" problem:

```
When the user asks you to modify specific items, revise ONLY those items.
Return revised items with the same proposal ID and incremented revision number.
Do NOT regenerate the full list unless explicitly asked.

Current plan state:
- [p1] APPROVED: "Easter Egg Hunt Prep" (Mon 4/13)
- [p2] PROPOSED: "Bunny Brunch Recipe" (Tue 4/14)
- [p3] PROPOSED: "Spring Garden Salad" (Wed 4/15)
```

### Client: Streaming UI

- Replace the `loading` boolean + spinner with a streaming text buffer
- Tokens append to a growing message bubble in real-time
- When `proposals` event arrives, render proposal cards below the message
- Smooth scroll follows the streaming text

### Future: Tool-Use Transparency

The SSE protocol is designed to support future tool events:

```
event: tool_start
data: {"tool": "calendar_list", "input": {"month": "2026-04"}}

event: tool_result
data: {"tool": "calendar_list", "summary": "Found 12 items in April"}
```

Not implemented in this phase, but the client should render unknown event types gracefully (collapsed "agent is working..." indicator). When agents gain tool access during brainstorming (checking calendar conflicts, searching existing content), these events will surface naturally.

## Phase 3: Review Panel + Two-Stage Approval

### Layout Change

The brainstorm view transforms from a full-width chat into a **split layout**:

```
┌─────────────────────────────────────────────────────┐
│  Session Header: title (editable), agent, status    │
├──────────────────────────┬──────────────────────────┤
│                          │                          │
│   Chat Panel (left)      │   Review Panel (right)   │
│                          │                          │
│   Conversation history   │   Proposed Items list    │
│   with streaming msgs    │   - status chips         │
│                          │   - approve/reject btns  │
│                          │   - click to edit         │
│                          │   - inline field editing  │
│                          │                          │
│                          │                          │
│   ┌──────────────────┐   │                          │
│   │ Message input     │   │   ┌──────────────────┐  │
│   └──────────────────┘   │   │ Confirm Plan [n]  │  │
│                          │   └──────────────────┘  │
├──────────────────────────┴──────────────────────────┤
│  (optional) calendar mini-view showing affected days │
└─────────────────────────────────────────────────────┘
```

**Responsive behavior:** On narrow viewports, the review panel becomes a slide-over drawer toggled by a button.

### Review Panel

The right panel shows **all proposals** from the session as a structured list:

- Grouped by date (sorted chronologically)
- Each card shows: title, date/time, contentType badge, tone badge, channel tags, status chip
- Status chips: `proposed` (neutral), `approved` (green check), `rejected` (red x, muted), `revised` (amber, shows revision count)
- Action buttons per card:
  - Approve (checkmark) — sets `status: 'approved'`, persists to session file via `PUT /sessions/:id/proposals/:proposalId`
  - Reject (x) — opens small inline input for rejection note, sets `status: 'rejected'`
  - Edit (pencil) — opens item in the detail drawer for field editing (see Phase 4)
- Rejected items collapse to a single line (title + "rejected" chip)
- Clicking a proposal card in the review panel scrolls the chat to the message that generated it

### Approval Flow

**Stage 1: Soft approval during planning**
- Clicking approve/reject on individual proposals in the review panel
- These are local to the session — no CalendarItems created yet
- Agent sees the current approval state in its system prompt context, enabling targeted conversation

**Stage 2: Confirm Plan**
- "Confirm Plan" button at bottom of review panel, shows count of approved items
- Disabled if zero items approved
- On click, calls `POST /sessions/:id/confirm`:
  1. Creates a `CalendarItem` (status: `draft`) for each approved proposal
  2. Links each proposal to its CalendarItem via `calendarItemId`
  3. Sets session status to `completed`
  4. Shows a success state: "Plan confirmed — N items added to calendar"
  5. Session becomes read-only (chat history viewable but input disabled)
- User can still navigate to created items on the calendar and edit them there

### Feedback Loop to Agent

When a proposal is rejected with a note, the next user message to the agent should include context:

```
[System note: Mark rejected "Bunny Brunch Recipe" with feedback: "needs to feature the easter bunny more prominently, not just a recipe"]
```

This is injected automatically before the user's next message so the agent can respond to the feedback naturally.

## Phase 4: Manual Editing

### Edit Targets

Any proposed item (in the review panel) or calendar item (on the calendar) can be edited via the existing detail drawer pattern. Editable fields:

| Field | Where | Notes |
|-------|-------|-------|
| `title` | Review panel + calendar drawer | Free text |
| `brief` | Review panel + calendar drawer | Textarea, this is the primary content planning field |
| `scheduledAt` | Review panel + calendar drawer | Date + time picker |
| `contentType` | Review panel + calendar drawer | Select from configured types |
| `tone` | Review panel + calendar drawer | Select from configured tones |
| `channels` | Review panel + calendar drawer | Multi-select from configured channels (Phase 5) |

### Interaction

- **Review panel:** Click the edit (pencil) icon on a proposal card → opens the BakinDrawer with an edit form pre-filled with proposal data. Save updates the proposal in the session file via `PUT /sessions/:id/proposals/:proposalId`.
- **Calendar views:** Click a calendar item → opens the existing item-detail-drawer, which gains the missing fields (brief is already there, but ensure all fields are editable including draft content fields).
- **Inline title editing:** In the review panel, the title is directly editable on click (contentEditable or input swap) for quick tweaks without opening the drawer.

### Draft Content Editing (Calendar Items)

Extend the existing item-detail-drawer edit mode to include draft fields:
- `draft.caption` — textarea
- `draft.imagePrompt` — textarea
- `draft.videoPrompt` — textarea
- `draft.agentNotes` — textarea (read-only display, agent-generated)

These fields are only relevant after an agent has produced draft content (post-execution), but the form should show them when present.

## Phase 5: Configurable Channels

### Settings

Add to calendar plugin `settingsSchema`:

```typescript
{
  key: 'channels',
  type: 'string',
  label: 'Distribution channels',
  description: 'Comma-separated list of available channels (e.g. discord, instagram, email, tiktok)',
  default: 'discord',
}
```

Parsed at runtime into an array. Used to populate multi-select dropdowns throughout the UI.

### Data Model Changes

**CalendarItem:**
```typescript
// Replace single channel field:
channel: ContentChannel        // DEPRECATED — keep for backward compat reads
channelTarget: string          // DEPRECATED

// Add:
channels?: string[]            // e.g. ['email', 'instagram', 'tiktok']
```

Read logic: if `channels` is present, use it. If not, fall back to `[channel]` for old items.

**ProposedItem** already has `channels?: string[]` from Phase 1.

### UI Changes

- **Review panel / edit drawer:** Multi-select chip input for channels, populated from plugin settings
- **Calendar views (month/week/list):** Small channel icons or initials shown on item cards (e.g. "IG" "EM" "TT")
- **Facet filter:** Add a channel filter to the calendar header using `FacetFilter` + `useQueryArrayState('channel')`
- **Agent system prompt:** Include allowed channels in persona context so the agent can suggest channel-appropriate content

### MCP + CLI Updates

**Exec tools** — update existing tools to support `channels`:
- `bakin_exec_calendar_create` — add `channels?: string[]` param
- `bakin_exec_calendar_update` — add `channels?: string[]` param
- `bakin_exec_calendar_list` — add `channel?: string` filter param (matches any item containing that channel)

**CLI** — update existing commands:
- `bakin calendar create` — add `--channels discord,instagram` flag
- `bakin calendar list` — add `--channel instagram` filter flag

### Not in Scope

Channel-specific content variants (different caption for Instagram vs. email) are explicitly out of scope. Each CalendarItem is one piece of content tagged with where it should go. Breaking into channel-specific tasks happens downstream when cron jobs pick up the item — that's future work in the schedule/tasks plugins.

## Phase 6: Polish + Multi-Agent Future-Proofing

### Data Model: Multi-Agent Ready

The `PlanningSession` has a single `agentId` field today. To future-proof:

- Add optional `participants?: string[]` field (unused for now)
- The `ProposedItem` already carries its own `agentId` field (defaults to the session's agent). When multi-agent sessions arrive, different proposals can come from different agents
- Session list UI groups by agent today — ensure the layout works if an "All Agents" group appears later
- The system prompt builder should be a function that takes an agentId, making it easy to swap per-message in a future multi-agent mode

### Calendar Mini-View

Below the split chat/review layout, an optional collapsed panel shows a mini month-view highlighting days that have proposed content. This gives spatial context while planning ("we have nothing on Thursday"). Clicking a day scrolls the review panel to items on that date.

### Session Indicators on Calendar

On the main calendar views, items that were created from a planning session show a subtle link icon. Clicking it opens the source session, providing the "why was this planned" audit trail. This requires adding `sessionId?: string` to `CalendarItem` (set during confirm).

### Keyboard Shortcuts

- `n` — new session
- `Enter` — send message (existing)
- `Shift+Enter` — newline (existing)
- `Cmd+Enter` — confirm plan (when review panel focused)
- `a` — approve focused proposal
- `r` — reject focused proposal

### Empty State

When no sessions exist, show an onboarding state:
- Brief explanation of planning sessions
- Agent cards to start a session with
- "Start Planning" CTA per agent
